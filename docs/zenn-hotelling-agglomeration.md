24時間配信している街のシミュレーション（[MESA](https://github.com/oggata/mesa-clouds-renderer)）に、経済学の「ホテリングの法則」を入れてみました。

やりたかったのは単純で、**ラーメン屋の隣にラーメン屋が建つ街**です。実際の街ではそうなります。ところが実装して回してみると、店は散らばったまま。「効いていないのか、つまみが悪いのか」を確かめようとしたところから、記事のほとんどを占める計測との戦いが始まりました。

結論を先に書くと、**最初に出した「効果あり」の数字は完全な誤読でした**。しかもその誤読は、指標の定義を紙の上で分解するまで気づけないものでした。同じ罠は自作のシミュレーションで測るときに広く踏みうるので、その過程を残します。

## ホテリングの法則と、実装したルール

ホテリングの法則は「競合は互いに近づく」という話です。海水浴場に2軒のアイス屋があると、客を取り合った結果どちらも浜辺の中央に寄っていく。現実の街で飲食店街や電気街ができるのも、大枠では同じ力（**集積の経済**）で説明されます。

ただし近づきすぎると今度は客を食い合う（**混雑の不経済**）。この綱引きが均衡を決めます。

実装は、住民が店を評価するときの報酬に2項足すだけです。

```js
const AGGLO_R = 3;        // 近隣とみなす距離 (セル)
const AGGLO_GAIN = 0.06;  // 近隣店1軒あたりの利益
const AGGLO_MAX = 0.30;   // 集積の利益の上限
const CROWD_MAX = 0.90;   // 混雑の罰の上限

// 自分の店は数えないので 1 を引く
const aggloBonus = (r, c) =>
  Math.min(AGGLO_MAX, Math.max(0, shopsNear(r, c) - 1) * AGGLO_GAIN);

// 来店の評価 = 近さ + 集積の利益 − 混雑
```

新しい店を建てる場所を選ぶときにも同じ考えを効かせます。

```js
function siteScoreDemand(cat, r, c) {
  // ... 需要の濃さ ...
  return s * (1 + SITE_AGGLO * Math.min(1, shopsNear(r, c) / 4));
}
```

つまみは `AGGLO_MAX`（集積の利益の上限）と `CROWD_MAX`（混雑の罰の上限）の2つ。この比率で街の姿が決まるはずです。

## 問題：確かめるのに何十日もかかる

効いているかを見るには、店が何度も開業・閉店するだけの時間を回す必要があります。ところが配信用の設定では**ゲーム内1日 = 実時間24分**。30日を見るのに12時間かかります。つまみを7通り試すなら数日です。

「1日を短くすればいい」と思って `DAY_MINUTES` を下げると、これが罠でした。ゲーム内時計が実時間から作られていたためです。

```js
function gameHour() {
  const elapsed = (Date.now() - _bootMs) / 1000;   // ← 実時間に縛られている
  return (START_HOUR + elapsed / (DAY_MINUTES * 60) * 24) % 24;
}
```

`DAY_MINUTES` を下げると、1日あたりの**tick数（住民が判断して歩く回数）まで一緒に減ります**。実測で `DAY_MINUTES=0.4` のとき1日160tick、来店0.1件/日。速いのではなく、住民がほとんど動かない**粗い別の街**になっていました。

### 時計をtick起点にする

なので時計をtickの数から作るように変えました。

```js
let _simTicks = 0;
const simNow = () => _bootMs + _simTicks * TICK;

function gameHour() {
  const elapsed = (simNow() - _bootMs) / 1000;
  return (START_HOUR + elapsed / (DAY_MINUTES * 60) * 24) % 24;
}
```

これで**1日あたりのtick数は通常運転と同じまま**、それを全速力で消化できます。描画と配信を止めて回すモードを足した結果が以下です。

| | 1実秒あたりに進むゲーム内時間 |
|---|---|
| 通常運転 | 0.93 ゲーム分（45実秒で42ゲーム分） |
| 早送り | 338.8 ゲーム分（34実秒で8ゲーム日） |

**363倍**。8ゲーム日が34秒で終わります。

### 使い分けの決まりを先に決めておく

ここで大事なのは、`simNow()` と `Date.now()` の使い分けを**決まりとして書いておく**ことでした。

- `simNow()` … 街の中の出来事（立ち話・娯楽・工事・天気・配達）
- `Date.now()` … 画面と外部（カメラ・HUD・チャット・配信・保存の間隔）

迷ったら「早送りしても意味が通るか」で決めます。カメラの切替間隔が363倍速で切り替わっても困るだけなので、あれは実時間でいい。

決まりを作ってから既存コードを見直したら、案の定混ざっていました。

```js
function finishConstruction() {
  const now = Date.now();          // ← ここだけ実時間のまま残っていた
  for (const st of CITY.structs) {
    // doneAt は simNow() 由来。早送りでは simNow() が Date.now() を大きく
    // 追い越すので、この条件が永遠に満たされない
    if (st.state !== 'construction' || !st.doneAt || now < st.doneAt) continue;
    st.state = 'open';
  }
}
```

**工事が永久に終わりません。** 早送りで建設中の建物が3→28軒に滞留して発覚しました。天気・配達・荷物の期限にも同じ混在があり、まとめて直しました。

:::message
実時間に縛られた設計を外すと、こういう「時計の混在」が一気に表に出ます。早送りは性能のためだけでなく、**バグを炙り出す装置**として効きました。
:::

## 最初の掃引：全部同じ数字が出た

準備ができたので、`AGGLO_MAX` を 0（対照群）〜0.7 で振って11run回しました。

見ていたのは**集積指数**です。

```
集積指数 = 実際の近隣店数の平均 ÷ 無作為に置いたときの期待値
```

1.0 なら無作為配置と区別がつかない、1.0 を超えていれば寄り集まっている、という設計です。結果がこちら。

| 集積 / 混雑 | 店 | 指数 |
|---|---|---|
| **0 / 0.9（対照群）** | 4 | **1.361** |
| 0.3 / 0.9 | 4 | **1.361** |
| 0.5 / 0.55 | 4 | **1.361** |
| 0.7 / 0.55 | 4 | **1.361** |
| 0.3 / 0.45 | 6 | 0.544 |
| 0.3 / 0.45 | 5 | 0.816 |

11run中8runが、**集積を切った対照群とまったく同じ 1.361**。

この時点で「効いていない」とは分かります。危なかったのは残りの3runで、素直に読むと「混雑0.45にすると指数が0.544まで落ちる＝混雑の罰が集積を壊している」という、**もっともらしいストーリーが書けてしまう**ことでした。

### 指数を分解する

定義に戻って、指数から実際の近接ペア数を逆算してみます。

```
指数 = avg / rnd
  avg = 各店の「半径3以内にある他店の数」の平均 = 2 × ペア数 / n
  rnd = (n − 1) × 49 / 400     ← 無作為配置での期待値（n = 店数, 20×20）
```

これを実測値に当てはめると：

| 店数 n | 指数 | 逆算した近接ペア数 |
|---|---|---|
| 4 | 1.361 | **1.00** |
| 5 | 0.816 | **1.00** |
| 6 | 0.544 | **1.00** |

**全11runで、近接している店のペアはちょうど1組。**

指数が 1.361 → 0.544 と動いて見えたのは、分子（実際の近さ）ではなく**分母の店数**が変わっただけでした。式にすると、この実測データは完全に

```
指数 = (2 / n) ÷ ((n − 1) × 49 / 400)
```

の1本の曲線に乗ります（誤差0.001未満）。街の空間構造は、どの条件でも**一度も変わっていなかった**わけです。

「混雑0.45は集積を壊す」に見えた3runは、単に**店が2軒多く開いて、それがたまたま離れていた**だけでした。

:::message alert
「無作為配置の期待値で割っているから店数で正規化されている」——そのつもりで作った指標が、実際にはnに強く依存していました。**正規化したつもりは、正規化できている保証になりません。**
:::

## なぜ何も動かなかったのか

原因は掃引ツールのこの1行でした。

```js
// 保存済みの本番の街をコピーして、そこから再開していた
fs.copyFileSync(SEED_STATE, state);
```

建物24軒と道の配置を最初から引き継いでいたので、15日で新しく開業・閉店する店はせいぜい1〜2軒。**立地ルールが働く余地がほとんどありません**。測っていたのは引き継いだ街のかたちであって、つまみの効果ではありませんでした。

ついでに、同じ条件を2回ずつ回して「再現性がある」と思っていたのも誤りでした。街の種が同じなので、**同じrunを2回見ていただけ**です。

## 実験を作り直す

3点直しました。

**① まっさらな村から始める。** 種ファイルを渡さず、建物12軒の村から立ち上げます。これで全ての店が「いま試しているルールのもとで」開業します。repごとに街の種も変えました。

**② 80日回す。** 15日では店の入れ替わりが足りません。

**③ 店数から独立した指標にする。** [Clark-Evans の最近隣指数](https://en.wikipedia.org/wiki/Nearest_neighbour_distribution)に替えました。実測の最近隣距離の平均を、無作為配置での期待値で割ります。

```js
// R < 1 … 寄り集まっている / R ≈ 1 … 無作為 / R > 1 … 散っている
let sum = 0;
for (let i = 0; i < n; i++) {
  let best = Infinity;
  for (let j = 0; j < n; j++) {
    if (i === j) continue;
    const dr = open[i].r - open[j].r, dc = open[i].c - open[j].c;
    const d = Math.sqrt(dr * dr + dc * dc);
    if (d < best) best = d;
  }
  sum += best;
}
const nn = sum / n;
const expect = 0.5 / Math.sqrt(n / cells);   // 密度から決まる期待値
const ce = nn / expect;
```

そして**生の値を必ず一緒に出す**ようにしました。近接ペア数、開業数、閉店数。指標の解釈を間違えても、後から検算できるようにするためです。前回の失敗はまさにここが無くて気づけませんでした。

### 対照群が理論値に落ちた

回し直した結果、いちばん重要だったのはこれです。

| | 対照群（集積0）のCE |
|---|---|
| 旧・集積指数 | 1.361（無作為なのに「集積している」） |
| Clark-Evans | **0.993**（無作為の理論値1.0とほぼ一致） |

集積を切った街が、無作為配置とちゃんと区別がつかない値になりました。**指標が較正できている**ことの確認です。

これは指標を作ったら必ずやるべきだったことでした。対照群を通して理論値が出るか確かめる。前回の指標はこれをやっていれば、1回目で捨てられました。

効果の向きも理論どおりでした（店数の影響を除いた偏相関）。

| | 偏相関 | t値 (df=11) |
|---|---|---|
| CE ↔ 集積の上限 | −0.421 | −1.54 |
| CE ↔ 混雑の上限 | +0.543 | **2.14** |

集積を上げると寄り集まり、混雑の罰を上げると散る。ただし有意水準 |t|>2.18 に対して**あと0.04届いていません**。「効果がある」と言うにはまだ足りない、というのが正直なところです。

## 本当の壁：街が店を3軒しか支えられない

ここで別の問題にぶつかりました。**80日回しても店が3〜5軒までしか増えません。**

人口86人・満たされていない需要が13000あってもです。店の生存条件は「1日の来客収入 ≥ 維持費8.75」で、ラーメン1杯6なので**1日2人来れば黒字**。それでも増えない。

日数を増やしても、`FOUND_SITE`（起業の発火閾値）を1/10に下げても変わりませんでした。人口を最初から120人にして始めると、今度は**11日で53人まで崩壊**します。

ログを見て原因が分かりました。

```
[Life] 拠点: 人口120 / 住居33軒(定員66) / 職場47件(定員36) ⚠ 定員超過54人
```

人口120に対して住居定員66・職場定員36。開始時点で家なし54人・職なし約84人。彼らが転出し、需要が消えて店が潰れる、という連鎖でした。

### 定員の計算が二重管理になっていた

掘ってみると、定員の計算が2箇所にあって食い違っていました。

```js
// 経済モジュール：建物の大きさで定員を決める（正しい）
const capacityOf = (S, size) => Math.max(1, Math.round(S.cfg.capUnit * size));

// サーバ側：軒数 × 固定値（大きさを見ていない、店の雇用も数えていない）
function workplaceCapacity() {
  return openStructsOf(WORK_IDX).length * WORK_CAP;
}
```

住宅も同様で、種類ごとの固定値（一戸建て2人 / 集合住宅12人）。**2x2の大きなマンションでも12人**しか住めない計算でした。

しかもこの `workplaceCapacity()` は「働き口が足りているか」の判定に使われます。つまり**街が職場不足を検知できていませんでした**。`職場47件(定員36)` という、件数より定員が少ない矛盾したログがその証拠です。

### 定員を大きさ基準に統一する

定員の定義はサーバ側が持ち、経済モジュールはそれを受け取る形に一本化しました。

```js
// 定員 = 単位 × 密度 × 大きさ(fp² × height)
const homeCapOf = st => {
  const dens = st.typeIdx === IDX_OF('apartment') ? APT_DENSITY : 1.0;
  return Math.max(1, Math.round(HOME_CAP_UNIT * dens * structSize(st)));
};
```

あわせて「1マスは1戸ではなく分譲住宅の1区画（4〜6戸）」と見立てて、定員そのものも上げました。オフィスも「1棟に会社がいくつも入っている」として5倍に。ただし**維持費も同じ倍率にして「定員の50%が埋まって収支ゼロ」という関係は保っています**。ここを崩すとオフィスが無条件に黒字になってしまうので。

| | 変更前 | 変更後 |
|---|---|---|
| 一戸建て 1x1 | 2人 | 12人 |
| 一戸建て 2x2 | 2人 | 48人 |
| 集合住宅 2x2 | 12人 | 144人 |
| オフィス 1x1 | 7人 | 33人 |
| 店1軒の雇用 | 2人 | 10人 |

結果、**店が9軒まで増えました**。近接ペアも0〜2から8へ。ずっと3〜5軒で頭打ちだった壁を初めて抜けています。

## そして、集積を入れると店が減った

条件が揃ったので対照群と比べたところ、予想と逆の結果が出ました。

| 集積 | シード | 人口 | 店 | 近接ペア |
|---|---|---|---|---|
| 0（対照） | A | 81 | **9** | 8 |
| 0（対照） | B | 75 | **5** | 1 |
| 0.5 | A | 133 | **3** | 0 |
| 0.5 | B | 72 | **3** | 0 |

集積を入れると、両シードとも**きっかり3軒・近接ペア0**。

筋としては「集積ボーナスで新店が既存店の近くに寄る → 同じ客を食い合う → 潰れる」で、**寄り集まるどころか店自体が生き残れない**。ホテリングの法則を入れたつもりが、混雑の不経済のほうが勝っている状態です。

各条件2runなので確定ではありませんが、方向は2シードで一致しています。

そしてここで、自分で入れたガードが裏目に出ました。「CEは店が3〜4軒だと雑音なので、6軒未満のrunは判定から外す」というルールを入れていたのですが、これは**いちばん効果が出ている集積アームを丸ごと捨てます**。

見るべき指標がCE（配置の偏り）ではなく、**店の生存数**だったわけです。

## 学んだこと

シミュレーションを自作して自分で測る、という状況に一般化できそうなものを挙げます。

**指標は必ず対照群を通す。** 「機能を切った状態」で理論値（無作為なら1.0）が出るか確かめる。旧指標は対照群が1.361でした。これを1回やっていれば、11run無駄にせずに済んでいます。

**指標と一緒に生の値をログに出す。** 近接ペア数さえ出していれば、「どの条件でも1組で一定」に即座に気づけました。指標だけ見ていると、分母が動いているのか分子が動いているのか区別がつきません。

**「正規化したつもり」を疑う。** 期待値で割れば規模に依存しない、とは限りません。実測データを指標の定義式に代入し直して、何が動いて何が動いていないか分解する。

**再現runは条件を本当に変える。** 同じ乱数種で2回回しても再現性の確認にはなりません。

**測定できないなら、まず測定できる状態を作る。** この件で実質的に効いたのは、集積のつまみを触ったことではなく、363倍の早送りと、定員のバグ修正でした。効果を測る前に、**効果が現れうる状態に街を持っていく**必要がありました。

**速く回すと、遅いと出ないバグが出る。** 時計の混在で工事が終わらない問題も、フィールド拡張時に日次処理が落ちる `ReferenceError` も、早送りで初めて表に出ました。後者は配信中の本番でも街が広がった瞬間に踏むもので、**遅く回している限り何ヶ月も気づけなかった**バグです。

## おわりに

ホテリングの法則の実装そのものは20行程度です。それが効いているかを言えるようにするまでに、時計の作り直し、指標の作り直し、定員の計算の統一、と回り道をしました。

現時点で言えるのは「実験が機能するようになった」ことと「集積を入れると店が減る（2シードで一致）」まで。**効果があると結論するのはまだ早い**、というのが正直な状態です。
