# 街が変わっていく — 不可逆な蓄積の仕様 (v1)

配信を毎日見ても飽きないようにするための変更。狙いは一つ:
**「昨日と違う」を街そのものに刻む**こと。エージェントの一日は毎日同じでいい。
街のほうが変わっていれば、視聴者は見続ける理由を持つ。

対象は `server.js` (配信サーバ) のみ。`standalone/index.html` はブラウザ単体版で
sim を別実装しているが、配信していないので v1 では触らない。

**街は完成品ではなく、村から始めて育つ。** 最初は低い建物が十数軒と住民が数人だけで、
住居が建つと人が増え、人が増えると需要が生まれて店が建ち、経済が回ると背の高い建物と
大きな施設が解禁される。その全体像は **§11「街の成長」**。

---

## 0. 前提条件 — ALIGNED 世界が必須

変更前の既定は LEGACY 世界だった:

```
PASSABLE = {ROAD, BUILDING}     // 空き地(OTHER)と木(TREE)は通れない
```

つまりエージェントは**道路と建物の中しか歩かない**。空き地は一歩も踏まれないので、
「踏み跡が道になる」は LEGACY では原理的に発火しない (踏み跡ゼロ)。

ALIGNED 世界 (`WORLD_ALIGNED=1`) では:

```
PASSABLE = {ROAD, OTHER}        // 道路と空き地は通れる / 建物と木は通れない
```

`planPath` は空き地に `COST_OFFROAD`(既定4) を与えて道路優先を保つ。
つまり **「基本は道沿い、でも急ぐと空き地を突っ切る」** という、踏み跡が生まれる
のにちょうどいい条件がすでに揃っている。

### 方策の再学習は不要

`MOVE_MODE = 'pursuit'` がハードコードされているため、
**現在 ONNX 方策は移動に使われていない** (`prefetchAllActions` も pursuit なら即 return)。
移動は A* + 決定論追従。したがって「LEGACY で学習した重みが ALIGNED で壊れる」という
既存コメントの懸念は、今日の配信構成には当てはまらない。

将来 policy モードに戻すときは、ALIGNED で学習し直した重みが要る (既存の注意書き通り)。
その時も本仕様の追加分は観測を変えないので追加の制約は生まない
(**建物は既存25種からしか建てない**ので goal の25次元 one-hot も不変)。

> 決定: ALIGNED を既定にした (`WORLD_ALIGNED=0` で LEGACY に戻せる)。
> LEGACY のままなら §2 (踏み跡) だけが無効になり、他の3機能 (起業/盛衰/初回性) は動く。

### 切替時に見つかった既存バグ (修正済み)

ALIGNED で 40 体を 60 秒動かしたところ、**1体あたり到着1回**しか起きず、多くが
建物の前で足踏みしていた。原因は `stepNavigate` の到着判定:

```js
if (a.pathIdx >= a.path.length-1 && dlast < 0.8) return true;   // 建物中心まで 0.8
```

ALIGNED では建物セルに立てないので、玄関に着いた人は建物中心まで 1.0 の位置で
前進を拒否され、**永久に到着しない**。`world.js` に ALIGNED 用の
`MW.hasArrived()` (4近傍で到着) が用意されていたのに、どこからも呼ばれていなかった。
到着しなければ来客も数えられないので、本仕様の前提として先に直した。

## 1. 設計の中心 — `CITY` 恒久状態

いまワールドの状態は3か所に散らばっている:

| 変数 | 中身 | 問題 |
|---|---|---|
| `MAP` | セル種別 30×30 | `makeMap(GRID,42)` で毎回同じ |
| `BUILDING_TYPES` | `"r_c" -> typeIdx` | **buildScene が毎回振り直す** |
| `scene` のメッシュ | 描画 | 型割当と生成が同じ関数の中で癒着 |

このままだと「1軒建てるたびに全部作り直し」になり、蓄積が消える。
そこで蓄積するものを1つのオブジェクトに集約する。

```js
const CITY = {
  version: 1,
  seed: 42,                    // マップ生成 seed。合わないセーブは読まない
  grid: 30,
  dayBase: 0,                  // 起動時点までに経過したゲーム内日数 (永続)
  bornAt: 1755600000000,       // 街の誕生時刻 (実時刻ms)

  // MAP は従来どおりモジュール変数のまま (書き換えの正)。保存/復元の対象。
  // BUILDING_TYPES と cellStruct は structs から syncCity() で毎回作り直す派生表。
  //   BUILDING_TYPES … 見た目/レイキャスト用。閉店中・工事中の建物も載る
  //   「行き先に選べるか」は st.state で判定する (buildingsOfTypes / pickBuildingOfType)

  structs: [                   // 建物1軒 = 1エントリ (2x2 は左上セルが代表)
    { r:12, c:7, fp:1, typeIdx:5,
      state:'open',            // 'open' | 'construction' | 'closed' | 'gone'
      born: 0,                 // 建った日 (0 = 創世時からある)
      openedBy: null,          // 起業した住民の aid (創世建物は null)
      visits: 0,               // 累計来客
      visitsToday: 0,
      ema: 0,                  // 来客数の指数移動平均 (閉店判定に使う)
      firstCustomer: null,     // 最初の客の aid
      doneAt: null,            // 工事完了予定 (ゲーム内時刻)
    }
  ],

  foot:   Int32Array(900),     // 踏み跡カウンタ (空き地セルのみ意味を持つ)
  demand: { eat:Float32Array(900), shop:Float32Array(900),
            fun:Float32Array(900), care:Float32Array(900) },   // 需要ヒートマップ
  unmet:  { eat:0, shop:0, fun:0, care:0 },                    // 不満の積分 (カテゴリ別)

  news: [ {t, day, kind, text} ],   // 直近200件。ティッカーと /city が読む
  stats: { roadsBorn:0, shopsOpened:0, shopsClosed:0 },
};
```

### `buildScene` の分割 (最初にやる refactor)

```
planCity(map)            … 1x1/2x2 の検出と型割当。CITY が新規のときだけ呼ぶ (現行の前半)
buildScene(map, CITY)    … CITY.structs からメッシュを生成するだけ (現行の後半)
```

これで「シーンを作り直しても街は変わらない」が成立する。
さらに追加/閉店した1軒だけを差し替えられるよう、struct にメッシュ参照を持たせる
(`occluders[key+'_b'].mesh` が既にあるので、これを正として使う)。

### 部分更新の粒度

| 変更 | 再構築するもの | コスト |
|---|---|---|
| 建物 1軒 追加/閉店/取壊し | そのメッシュ1個だけ | 無視できる |
| 空き地 → 道路 | 道路/地面/摩耗のマージ済み quad メッシュ3枚 | 900 quad ≒ 1ms、1日1回 |
| トレイル | 触らない | — |

建物は元から**個別メッシュ**で描かれている (近接フェードのため)。
`mergeGeos` は道路と地面の板だけ。したがって「1軒足すと全部作り直し」問題は実は
存在せず、道路の板だけ差分更新すればいい。

## 2. 機能A — 踏み跡が道になる

### 測る
`stepAll()` の前進成功地点 (`a.visited` を更新している所) で:

```js
if (MAP[r][c] === OTHER) CITY.foot[r*GRID+c]++;
```

道路の上の足跡は数えない (既に道なので情報がない)。

### 見せる (連続)
踏み跡は**閾値を超える前から見えている**必要がある。ある日突然アスファルトが
生えるより、土が露出していく方が「蓄積」に見える。

地面 quad を3枚のマージ済みメッシュに分ける:

| 段階 | 条件 | 色 |
|---|---|---|
| 草地 | それ以外 | `0x9ccc65` (現行) |
| 踏み固め | 踏み跡のある空き地の**上位20%** かつ `foot ≥ WEAR_1` | `0xa8a878` |
| 露出 | **上位5%** かつ `foot ≥ WEAR_2` | `0xb9a97e` |

**絶対数ではなく上位%で塗る**。300体では1分で 500 踏みに達したので、絶対閾値だと
人数しだいで空き地が一面茶色になる。上位%なら常に「いちばん踏まれている一部」だけが
土になり、道の生まれる筋がそのまま見える。`WEAR_1/WEAR_2` は下限として残す
(できたばかりの街で数踏みの差を土扱いしないため)。

再構築は道が増えたときは即座に、踏み跡の濃淡は 20 秒ごと (最短3秒間隔)。

### 昇格する (離散・1日1回)
毎日のロールオーバー (§6) で:

1. 候補 = `MAP[r][c]===OTHER` かつ **4近傍に ROAD がある**セル
2. `foot` 降順でソート
3. 上位から最大 `ROAD_PER_DAY`(既定2) 本を `ROAD` に昇格。ただし `foot >= FOOT_MIN`(既定 300)
4. 昇格したセルの `foot` は 0 に戻し、周囲8セルの foot を 1.5倍する
   (道は道を呼ぶ = 商店街が線状に伸びる)
5. 昇格しなかったセルは `foot *= FOOT_DECAY`(既定 0.9)
   — 一度の横断が何週間もかけて積み上がって全面道路になるのを防ぐ

**なぜ閾値ではなく日次ランキングか**: エージェント1000体・1体あたり毎秒3セル進むので、
絶対閾値は agent 数と TICK に強く依存して調整不能になる。「今日いちばん踏まれた空き地を
2本だけ道にする」なら、規模が変わっても1日の変化量が一定に保たれ、配信の
「毎朝2本ずつ道が伸びる」というリズムにもなる。

### 副作用
- `MAP` を書き換えるので `planPath` / `PASSABLE` / FPV レイキャストが自動的に追従する
- 道路を**足す**変更なので連結性は悪化しない (分断の心配は §3 の建築側だけ)
- ニュース: `🛣 空き地に道ができた (12,7)` — 出しすぎると安いので1日1件に集約

## 3. 機能B — 足りないものを住民が起業する

### 3.1 「足りない」を測る
需要 = **不満 × 距離の積分**。`stepNeeds()` (1Hz) の中で、欲求が閾値を超えている
エージェントについて:

```js
const n = needOf(a);                       // 'eat' | 'shop' | 'bored' | 'sick' のみ対象
const cat = NEED_TO_CAT[n];                // eat/shop/fun/care
const d = nearestDist(a, CAT_IDX[cat]);    // 最寄りの該当建物までのチェビシェフ距離
const w = clamp((d - D_OK) / (D_FAR - D_OK), 0, 1);   // D_OK=4, D_FAR=14 セル
CITY.unmet[cat] += w * dtSec;
CITY.demand[cat][cell(a)] += w * dtSec;    // どこで不満だったか
```

- 最寄りが `D_OK` 以内なら需要ゼロ。**近くにあるのに空腹**は供給不足ではない
- 該当建物が街に1軒も無ければ `w = 1`
- `nearestDist` は該当カテゴリの建物リストの線形走査。対象は「欲求が高い人」だけなので
  最悪 1000体 × 60軒 = 60k回/秒。既存の孤独判定 (1000² = 100万回/秒) より軽い

### 3.2 どこに建てるか
`CITY.demand[cat]` が「未充足の欲求を抱えた人が通った回数」のヒートマップになっている。

候補セル:
- `MAP[r][c] === OTHER` かつ 4近傍に `ROAD` がある (= 道に面している)
- **閉店した建物の跡地** (§4) は候補に優先的に含める。連結性チェックが不要で、
  跡地が再利用されるのは絵として強い
- 建てても**連結性が壊れない**こと (下記)

スコア = `demand[cat][cell]` + 近傍3×3の demand の平均 × 0.5。最大のセルを選ぶ。

§2 と組み合わさると **道ができる → 人が通る → 店ができる → さらに人が通る** が回る。
放っておくと商店街が創発するはず。これが本仕様のいちばん面白いところ。

### 3.3 連結性ガード (必須)
空き地を建物にすると、そこが唯一の通路だった場合に街が分断される。
`world.js` に道具が揃っているので、それを使う:

```js
const before = countPassable(MW.largestComponent(MW.passableMask(map, WORLD)));
map[r][c] = BUILDING;
const after  = countPassable(MW.largestComponent(MW.passableMask(map, WORLD)));
if (after !== before - 1) { map[r][c] = OTHER; /* この候補は捨てて次へ */ }
```

「最大連結成分がちょうど1セルだけ減った」= 誰も孤立していない。
BFS 1回 = 900セル、1日1回なので無視できるコスト。

さらに `MW.ensureAllBuildingsReachable` で「新しい建物に玄関があるか」も担保する。

### 3.4 何を建てるか
**既存25種の footprint=1 のみ**。方策の goal は25次元 one-hot なので、種類を増やさない
限り再学習は不要 (2x2 は4セル必要 + 連結性が壊れやすいので v1 では建てない)。

その結果、起業できるのは実際には次の8種になる:

| カテゴリ | 建てられる業種 |
|---|---|
| eat | 屋台 / ラーメン / 牛丼 / カフェ / 弁当 |
| shop | コンビニ / 商店 |
| care | 薬局 |
| fun | **なし** (競技場・神社・博物館・図書館は全部 2x2) |

`fun` は需要としては測るが起業対象外。2x2 の建設を入れるのが v2 の宿題。

カテゴリ内での種類選択は**近傍の希少性**で決める:
半径8セル以内に同タイプが少ないものを優先。同じ通りにラーメン屋が3軒並ぶのを防ぐ。

### 3.5 誰が建てるか
`personas.json` に `enterprise` (0..1, 既定 0.3) を追加する。

```json
{ "id":"D", "name":"Businessman Cole", "color":"#ffee00", "enterprise":0.8 }
{ "id":"B", "name":"Homebody Lily",    "color":"#00ccff", "enterprise":0.05 }
```

起業者 = `argmax(enterprise × そのカテゴリへの自分の不満寄与)`。
つまり「自分が一番困っていて、かつ性格的に動く人」。決定論なので再現できる。

副作用 (ここが**不可逆**の本体):
- `a.work = [r,c]`、`a.owns = [r,c]` — その住民の一日のルーチンが以後ずっと変わる
- `assignHomes()` は `a.owns` があれば `a.work` を上書きしない
- 店主は営業時間 (9-17時) に自分の店にいるので、店の周りに常に人がいる絵になる

### 3.6 発火の抑制 (飽和対策)

当初は「不満の総和 ÷ 供給軒数」を圧として使う設計だったが、**実測で常にゼロに潰れた**。
この街は 900セルに 139軒と密で、どのカテゴリも最寄りが 2〜3セル以内にあり、
「遠くて満たせない」人がほとんど居ないため。総和で見るかぎり永久に発火しない。

そこで発火条件を**場所ごと**に変えた:

```
score(cell) = demand[cat][cell]*2 + Σ(3x3 近傍の demand)*0.5     // agent-秒
発火 = max_cell score / (DAY_MINUTES*60) >= FOUND_SITE           // agent-day 単位
```

意味は「何人日ぶんの『遠くて満たせない欲求』がその一角を通ったか」。
街全体では足りていても、**一帯にだけ飲食店が無い**状況は拾える。
そして開店すればその一帯の人は `D_OK` 以内に店を持つので需要の流入が止まり、
飽和は自動的に収まる (グローバルな供給密度で割る必要がない)。

**1日あたり最大1件**。起業したら `unmet[cat] *= 0.4` に加えて、
**新しい店の周囲3セルの需要ヒートマップをゼロにする**。開店後は新たな需要が積もらない
一方で、過去に積んだ熱は減衰待ちで残るため、消さないと同じ場所が数日連続で最大スコアに
なり隣に同種の店が建ち続ける (実測: 2日で薬局2軒)。

実測値 (300体 / `DAY_MINUTES=2` / 既定閾値):

| 日 | eat | care |
|---|---|---|
| Day1 | 0.00 (最寄り平均 —) | 0.02 (4.1セル・遠い61%) |
| Day3 | 0.20 (2.5セル・遠い34%) | 0.28 (5.7セル・遠い89%) |

減衰 0.75 の平衡は日次流入の約4倍なので、この規模で 0.5〜0.8 に落ち着く見込み。
**本番 (1000体) はこの3倍前後**になるので、`FOUND_SITE=0.5` なら序盤は毎日1軒建ち、
街が埋まるにつれて自然に止まる。速すぎ/遅すぎならログの数字を見て調整する。

`FOUND_SITE` の既定 0.5 は暫定値。毎日のログに全カテゴリの score と
「最寄り平均距離 / 遠い割合」が出るので、1〜2日回してから決めること:

```
[City] 起業の圧 eat:0.12(39軒 最寄り平均2.1c 遠い3%) shop:0.44(20軒 ...) | 発火 0.5 agent-day
```

### 3.7 建つ / なくなる の演出

街の形が変わる瞬間は**必ず見せる**。人を追うカメラを一時的に止めて現場に寄り、
建物を動かし、画面に一言出す。

| できごと | 建物の動き | カメラ | 画面の一言 |
|---|---|---|---|
| 着工 | 工事の箱が地面から**せり上がる** | 現場に寄って回り込む (既定9秒) | 「カフェ の工事が始まりました」 |
| 開店 | 本体が地面から**せり上がる** | 同上 | 「Mika #1 の カフェ が建ちました」 |
| 閉店 | シャッター (色が沈む) | 同上 (7秒) | 「Cole #4 の 薬局 が閉店しました」 |
| 取り壊し | 建物が地面に**沈む** | 同上 | 「薬局 がなくなりました」 |

**地面より下は自然に隠れる。** 地面は W×W の不透明プレーン (z=0) で、カメラは常に
その上にあるので、`position.z` を下げるだけで「地中から出てくる / 地中に潜る」になる。
クリッピング平面は要らない。動きは ease-out で最後にふわっと止まる。

**アニメはカメラが着いてから動かす。** イベントは待ち行列に並ぶので、状態が変わった
瞬間に動かすと「カメラが到着したころには沈み終わっている」ことになる (実際になった)。
`showCityEvent(r, c, 一言, 秒数, {st, kind})` に渡すと、開始位置に置くところまでを
即座に行い、実際の動き出しはカメラがその場所に着いた時刻に合わせる。

**取り壊しは沈みきってから地面を書き換える。** 先に空き地にすると、まだ建物が
立っているのに人がすり抜けて見える。`state='demolishing'` の間は通行不可のままで、
アニメの完了コールバックで `MAP` とメッシュと一覧をまとめて片付ける。

一言は3D映像に焼き込むので YouTube 側にも出る (ティッカーとは別枠。ティッカーは
一周に時間がかかるので、その瞬間に見せたいものはバナーで出す)。

### 3.8 工事中の状態
即座にポップさせない。

1. 起業決定時: `MAP[r][c] = BUILDING`、struct を `state:'construction'` で追加。
   状態が `open` でないので誰も目的地に選ばない
2. 灰色の低い箱がせり上がる (§3.7)
3. `CONSTRUCTION_HOURS`(既定2ゲーム時間) 後に完成 → 本体がせり上がる
4. 最初の客が入ったら `firstCustomer` を記録してニュース (§5 と合流)

落ちている間に完成予定時刻を過ぎた建物は、起動時に開業済みとして扱う。
「住民が建てた店」は `st.founded` で区別する (初日に建った店は `born=0` で、
創世からある建物と見分けが付かなかった)。

## 4. 機能C — 店の盛衰

### 数える
到着地点 (`a.trips++` があった所) に `onArrive(a, dest)` を差し込む:

```js
const st = structAt(dest[0], dest[1]);
if (st) { st.visits++; st.visitsToday++; ... }
```

LEGACY/ALIGNED どちらでも到着イベントは同じ場所で起きるので分岐不要。

### 閉店
日次ロールオーバーで、**起業で建て直せる業種だけ**を対象に
(閉店しうる集合 = §3.4 の8種。潰れたきり二度と建たない業種を作らないため):

```
ema = ema*0.7 + visitsToday*0.3
```

閉店条件 (すべて満たす1軒だけ、1日最大1件):
- `state === 'open'`
- 築 `GRACE_DAYS`(既定3日) 以上 — 建ったばかりの店に猶予を与える
- `ema` が最下位、かつ `ema < 同業の ema 平均 × CLOSE_FRAC`(既定 0.25)
  — 絶対値だとエージェント数で意味が変わって調整不能になる (踏み跡を日次ランキングに
  したのと同じ理由)。「同業と比べて客が来ていない店」なら規模に依存しない。
  中央値ではなく平均なのは、店数が多いと半数以上が来客ゼロで中央値が 0 になり、
  条件が永久に成立しなくなるため。来客が均等なら平均の 25% を割る店が無くなり、
  閉店は自然に止まる (= 偏っている間だけ淘汰が起きる)
- そのカテゴリの営業中店舗数が `MIN_PER_CAT`(既定2) より多い — 飲食店が全滅しない

**住宅/職場/病院/学校/駅/市役所は閉店しない。**
自宅が消えると `assignHomes` の割当が壊れるし、病院が消えると病気が治らなくなる。
「潰れるのは店だけ」なら倫理的な据わりの悪さも一切ない。

閉店処理:
- `types` から削除 (誰も目的地に選ばなくなる)
- マテリアルを暗くする (`color.multiplyScalar(0.45)`) = シャッター表現。
  専用テクスチャを用意するならここを差し替えるだけ
- セルは `BUILDING` のまま = 連結性は変わらない
- ニュース: `🚪 ラーメン屋 (12,7) が閉店しました`

### 取り壊し → 空き地
`DEMOLISH_DAYS`(既定5日) 閉店したままなら `MAP[r][c] = OTHER` にしてメッシュを削除。
空き地に戻るので、また誰かが建てられる。連結性は改善方向なのでチェック不要。

これで **建物のレベルで生死が回る**。lifegame の生成消滅を、人ではなくインフラでやる形。

## 6. 機能E — 画面に出す (Day カウンタ / ティッカー)

### 日付の定義
`gameHour()` は起動時刻からの実時間で計算している。同じ式で日を出す:

```js
const elapsedDays = (START_HOUR + elapsed*24/(DAY_MINUTES*60)) / 24;
gameDay() => CITY.dayBase + Math.floor(elapsedDays);
```

`dayBase` を永続化するので、再起動しても Day は戻らない。
`gameDay()` の値が変わった瞬間に **`dailyRollover(day)`** を1回だけ呼ぶ
(踏み跡昇格 / 起業判定 / 閉店判定 / `visitsToday` リセット / demand 減衰 をここに集約)。

朝5時に切り替わるように `+ 5/24` のオフセットを入れる — 深夜に街が変わるより
「朝起きたら道ができている」ほうが配信の絵として自然。

### HUD 描画パス
YouTube に出ているのは 3D をそのまま rawvideo にしたフレームで、文字は一切乗っていない。
そこで描画を2パスにする:

```js
renderer.autoClear = false;
renderer.render(scene, mainCam);
renderer.clearDepth();
renderer.render(hudScene, hudCam);   // OrthographicCamera(-W/2, W/2, H/2, -H/2)
```

文字のラスタライズは **SVG → sharp → DataTexture**。`buildNeedIcons()`
で既に実績のある方法なので新しい依存は要らない。

| 要素 | 位置 | 更新頻度 |
|---|---|---|
| `DAY 47  08:32` / `POP 34  TOWN  SUNNY` | 左上 (250×54) | 最短1秒に1回 |
| ニュースティッカー | 下端の帯 (高さ30) | ニュース追加時にテクスチャ再生成、スクロールは板の x を動かすだけ |
| できごとのバナー | 上寄り中央 (高さ48) | イベント発生時のみ数秒 |

**焼き込む文字は ASCII だけにする。** 本番 (Linux) に日本語フォントが無く、
日本語を描くと全部豆腐になった。そこで HUD だけ英語にし、
ログ / `/city` / WebSocket は日本語のままにしてある。
そのために `news(kind, 日本語, 英語)` の3引数目と、建物名の英語表 `BLDG_EN`、
発展段階の `en` (HAMLET/VILLAGE/TOWN/CITY/METROPOLIS) を持っている。

漏れを防ぐ仕掛けを2段構えで入れてある:

1. **`_ascii()` で描画直前に非 ASCII を落とす**(日付板・ティッカー・バナーの3か所)。
   何かが混ざっても豆腐にはならず、その文字が消えるだけで済む
2. **`en` を持たないニュースはティッカーに流さない**。英語化する前に保存された街を
   復元すると、`data/city_state.json` の中の記録は日本語しか持っていない。
   そのまま描くと復元直後だけ豆腐が流れるので、英語のある記録だけを選ぶ
   (記録自体は残るので `/city` とログでは日本語で読める)

天気はティッカーに流さない (日付板に常時出ているうえ、変化が多くて街のできごとを
押し出してしまう)。`TICKER_SKIP` で除外している。

### 6.1 ティッカーの中身 — できごと と 住民の様子

開店/閉店だけだと事件の連続で、人が住んでいる感じが出ない。そこで
`LIFE_NEWS_SEC`(既定25秒) ごとにランダムな住民を1人選び、いまの様子を流す。

```
D5  Ramen Shop opened - run by Cole #11   *   Lily #2 is sleepy and heading home
    *   D5 Footpaths turned into 2 new roads   *   Rex #3 fell ill and is heading to a Pharmacy
```

- **街のできごとと住民の様子は別の枠**に貯めて、ティッカーで**交互に**並べる。
  同じ列に入れると、1日数件しかない開店/閉店が、数十秒ごとに出る住民の様子に
  押し出されてしまう。住民の様子は保存もしない (街の記録ではなく、その瞬間の景色)
- 抽選は状態で重み付けする (病気6 / 空腹3 / 退屈2 / 買い物2 / 睡眠1 / 勤務1)。
  一様抽選だと夜は「寝ている」ばかりになる
- 直近に出した住民は避け、さらに**名前と数字を伏せた「文の形」**が直近3件と
  重ならないよう数回引き直す。小さな村では全員が同じ状態 (勤務時間帯など) になり、
  名前だけ違う同じ文が並んでしまうため
- 言い回しは各状態に2〜3種類。勤務中は空腹/眠気を一言添える
  (`is on the way to work (already getting hungry)`)
- 3回に1回ほどは状態ではなく**来歴**を流す
  (`has been to 7 different kinds of places in town` / `runs the Ramen Shop in this town`)
- `/city` の `residents` で日本語と英語の両方を確認できる

ティッカーは幅2048pxのテクスチャを持つ板を毎フレーム左へ流す。ortho カメラの視錐台の外は
そのまま切られるのでクリッピング処理は不要。

`HUD=0` で無効化できるようにする (負荷が問題になったとき、あるいは
OBS 側で別途オーバーレイを入れたくなったとき用)。

### ブラウザ側
ブラウザ視聴者が見る JPEG も同じ描画結果なので、HUD はそのまま映る。
client.html 側に二重表示しない。ただし他の用途 (OBS のオーバーレイ、外部ダッシュボード)
のために `statsLoop` の WebSocket メッセージへ `day` と直近ニュース5件を足してある。

## 7. 永続化

`data/city_state.json` (`CITY_STATE_FILE` で変更可)。

- 保存: 60秒ごと + `SIGINT`/`SIGTERM` (既存の `shutdownYt` のハンドラに相乗り)
- 読込: 起動時。`version` と `seed` と `grid` が一致しなければ**読まずに新規生成**
  (マップ生成則を変えたときに壊れた街を復元しないため)
- サイズ見積り: structs 300 × 100B + foot/demand 900×5 + agents 1000×(aid,mask,owns)
  ≒ 200KB。JSON で十分
- `newmap` コマンドと `/city?reset=1` は CITY を破棄して作り直す (= 街の作り直し)

> ⚠️ **デプロイ先のディスクが永続かどうかの確認が要る。**
> Render の標準インスタンスはファイルシステムが揮発性で、再デプロイのたびに消える。
> その場合は永続ディスクをマウントするか、外部ストレージ (S3 等) に置くか、
> あるいは「プロセスが生きている間だけ蓄積する」と割り切るかの判断が必要。
> 蓄積が数時間で消えるなら本仕様の狙い (1週間ぶりの視聴者が別の街を見る) は達成できない。

## 10. 詰まりそうな箇所 (実装時に確認済み)

1. **`BUILDING_TYPES` の再生成** — buildScene が呼ばれるたび型が振り直されていた。
   `planStructures` に切り出して創世時のみに変更 (これをやらないと以降すべてが無意味)。
2. **到着判定** — ALIGNED では玄関で到着としないと、誰も店に着かない (§0)。
3. **連結性** — 空き地を建物にする前に `canBuildAt()` で最大連結成分を比較し、
   「ちょうど1セルだけ減る」ことを確認する。減り方が違えばその候補は捨てる。
4. **`assignHomes()` の再呼び出し** — `a.owns` があれば職場を上書きしない。
   起業した住民の職場が `reset` で元に戻らないようにするため。
5. **エージェント1000体** — `NUM_AGENTS` が `CAM_INTERVAL_MS` から読まれていて既定
   1000体になっている (server.js の書き間違いと思われる)。日次処理は O(セル数)、
   毎秒処理は O(agents × カテゴリ内軒数) に収めてある。
   ※ 別件だが `updateOcclusionFade()` が O(agents × occluders) を毎フレーム回している。
     1000体だと毎フレーム約60万回で、ここが一番重い。本仕様とは独立の既存課題。
6. **飽和** — 場所ベースの発火にしたので、開店するとその一帯の需要が止まって自然に収まる。
   それでも `FOUND_PER_DAY=1` の上限は残してある。
7. **ティッカーの安さ** — 「道ができた」は1日1件に集約。初回性ニュースは
   `FIRST_NEWS_COOLDOWN` で間引き、新店の初客・開業・閉店を優先する。
8. **日本語フォント** — ティッカーは sharp(librsvg) で描くので、Linux では
   `fonts-noto-cjk` が無いと豆腐になる。起動時に自己診断して警告を出す。

## 11. 街の成長 — 村から始めて育てる

「建物が建っていく様子」を見せるには、最初から完成した街があってはいけない。
そこで**村から始めて、人口と経済で育てる**。

### 11.1 フィールドそのものが小さく始まって広がる

マップ配列は `GRID`(30) 四方のままだが、**実際に世界として使うのは中央の
`CITY.size` 四方だけ**。外側は `VOID`(=4) にして、通行不可・描画なし・レイを止める。
地面の板もフィールドのぶんしか敷かないので、**街は宙に浮いた島**のように見え、
広がると島が大きくなる。

`makeMap` は 0〜3 しか返さないので、`VOID` は実行時にだけ現れる4つ目の種別。
**マップ生成には一切手を入れていない**ので学習側 (mesa_env) との bit 一致は保たれる。

最初は `START_SIZE`(既定10) 四方。土地が足りなくなったら1日1回、両側1セルずつ広がる:

```
拡張する条件 = 建て込み具合 > EXPAND_DENSITY(0.28)  または  空き区画 ≤ EXPAND_FREE(6)
```

**空き区画の数だけで判断してはいけない。** 建物が増えるほど「建物に接した空き地」も
増えるので、その数はなかなか減らず、いつまでも広がらなくなる。建て込み具合
(フィールドに占める建物セルの割合) を主な判断に使う。

新しく現れる土地は草地で、元の地形の木を `EXPAND_TREES`(既定3セルに1本) に間引いて
少しだけ生やす。一面の林にすると「建物が無くて木だけの場所」になってしまうため。
拡張の瞬間は引きの画で「街の範囲が広がりました (14×14)」と出す。

### 11.1b 最初の建物

生成された「完成した街」に対する後処理として間引く (`villageStart`)。

- フィールドの外は `VOID`、中の建物はいったん全部さら地に
- フィールド内で中心に近い区画を `START_BUILDINGS`(既定12) だけ選び、
  **1x1 の低い建物**として建て直す (元の建物跡を優先し、足りなければ道に面した空き地から補う)
- 用途は下の順に割り当てる。**生活に必要なものから先に揃う**ように並べてある:

```
house, house, post, kiosk, house, ramen, conbini, house, cafe, pharmacy,
house, bento, shop, house, gyudon   (以降くり返し)
```

12軒なら 住宅5 / 職場1 (郵便局) / 飲食4 (屋台・ラーメン・カフェ・弁当) / コンビニ1 / 薬局1。
**住む場所・働く場所・食べる場所は必ず入る。**

- 人口は `START_POP`(既定8) から。住居5軒 = 定員10 なので最初から全員に家がある

`START_VILLAGE=0` で従来の「完成した街」から始められる。

### 11.2 人口 — 家が建つと人が増える

**家が無い人は生まれない。** 人口の上限は**住居の定員**で決まり、
`growPopulation` は空きベッドのぶんしか転入させない。

| 建物 | 定員 |
|---|---|
| 🏠 住宅 | `HOUSE_CAP` = 2 |
| 🏬 マンション | `APT_CAP` = 12 (高さ2.1なので「町」から解禁) |

毎日、定員に空きがあるぶんだけ転入する:

```
転入数 = min(空き, MOVEIN_MAX(8), ceil(人口 × POP_GROWTH(0.15)))
```

住居が `HOME_PRESSURE`(0.85) を超えて埋まると、翌朝いちばん優先して住宅が建つ。
建てた家は工事 (2ゲーム時間) を挟むので、**定員が増えるのは翌日**。
人口は常に定員の少し下を追いかける形になる。

実測 (1日=1分の加速設定):

| 日 | 人口 / 定員 |
|---|---|
| Day2 | 10 / 12 |
| Day3 | 12 / 12 ← 満室 → 住宅を建てる |
| Day5 | 14 / 26 ← マンションが建って一気に増える |
| Day9 | 26 / 26 ← 満室 → また建てる |
| Day10 | 30 / 38 |

家なし 0人、定員超過の家 0軒 を `/city` で確認済み。

万一あふれた場合 (保存データの設定を変えた等) の受け皿も用意してある:
- 割当は**いちばん空いている家**へ (先頭の家に全員詰め込まない)
- 家の無い住民は最寄りの住居で休める (`pickLifeGoal` / `stepNeeds`)。
  これが無いと疲労が 1.0 で飽和したまま永久に徘徊する
- `/city` の `population.homeless` と起動ログの `⚠ 家なし` で観測できる
同じく勤め人が職場の定員 (`WORK_CAP`=6 × 職場数) の `WORK_PRESSURE`(0.9) を超えると
職場が建つ。**建設の優先順位は 住むところ → 働くところ → 商売**。生活の器のほうが先。

1日に建てられる軒数は人口に比例する (`1 + 人口/FOUND_PER_POP`、最大6)。
人が増えるほど街が速く育つ = 複利で伸びる。

拠点の割当 (`assignHomes`) は**既に住んでいる人をそのまま**にして空きへ入れる方式に
変えた。以前は index で機械的に割り当てていたので、家が1軒建つたびに全員の住所がずれ、
「引っ越してきた」が成立しなかった。

### 11.3 発展段階 — 経済が回ると高い建物が解禁される

経済活動 = **店/施設への来店の累計** (`CITY.econ`)。これが溜まると段階が上がり、
建てられる建物の**高さの上限**と **2x2 の可否**が緩む。

| 段階 | 高さ上限 | 2x2 | 経済 | 解禁されるもの (例) |
|---|---|---|---|---|
| 集落 | 1.4 | — | 0 | 住宅 / 郵便局 / 屋台 / コンビニ / カフェ / 薬局 |
| 村 | 1.7 | — | 400 | 銀行 |
| 町 | 2.1 | ✓ | 2,000 | マンション / スーパー / 神社 / 学校 / 駅 / 図書館 / 病院 / 市役所 |
| 市 | 2.6 | ✓ | 8,000 | オフィス / 博物館 / 競技場 / 複合ビル |
| 都市 | 3.3 | ✓ | 25,000 | タワー |

`ECON_SCALE` で発展の速さをまとめて調整できる (小さいほど早い)。

**業種は「街にいちばん少ないもの」から建つ。** 解禁された新種は必ず0軒なので、
段階が上がった瞬間にそれが建つ = 街が育つほど建物の種類が増えていく。
方策の goal は BLDG_TYPES(25) の one-hot のままなので**再学習は不要**。
変わるのは「いつ建つか」だけ。

段階が上がった瞬間は、引きの画で街全体を映して
「この街は 町 になりました」と出す (§3.7 の演出に `wide` オプションを追加)。

### 11.4 2x2 の建設

「町」以降は 2x2 が解禁されるので、`pickSite` は footprint 対応にした。

- `blockFree(r,c,fp)` … fp×fp が全部空き地か
- `facesRoadOrBuilding(r,c,fp)` … 道か既存の建物に接しているか
  (村のうちは道が中心にしか無いので「建物の隣」も許さないと街が広がれない)
- `canBuildFootprint(r,c,fp)` … 建てても最大連結成分が **ちょうど fp×fp セルしか
  減らない**か = 誰も孤立しないか

### 11.5 回っている輪

```
住居が建つ → 人が増える → 需要が増える → 店が建つ → 来店が増える
   ↑                                                      ↓
   └────── 住居が足りなくなる ←── 経済が回る ←── 段階が上がる ──┘
                                    (高い建物 / 大きい施設が解禁)
```

これに §2 の「踏み跡が道になる」が重なると、
**道ができる → 人が通る → そこに店が建つ → さらに人が通る**
も同時に回る。放っておくと商店街と道路網が勝手に育つ。

## 13. 配信チャットからの指示

視聴者が「このキャラを映して」と書くと、数秒だけそのキャラを追う。

```
test / ping         → 画面に「chat OK - <視聴者名>」と数秒出る (疎通確認)
!focus rex          → Explorer Rex #1 を 10秒追う
focus Lily #2       → 表示名で指定
focus B             → ペルソナ id で指定
focus 3             → 3人目
focus overview      → 俯瞰
focus random        → ランダム
```

画面には `Camera: Explorer Rex #1 (by <視聴者名>)` と数秒出る。
**自分の名前が配信に出る**のが、この機能のいちばんの価値だと思う。

カメラの優先順位は **チャットの指名 > 街のできごと > 自動切替**。
指名は数秒なので、その間に起きた着工/取り壊しは待ち行列で待ち、明けてから再生される
(アニメもカメラ到着に合わせて始まるので、見逃しにはならない)。

### 13.0b 届いているかの確認

チャットが**そもそも届いているのか**、届いたが**命令として解釈されなかった**のかは
別の話なので、3か所で見られるようにしてある。

| 見る場所 | 内容 |
|---|---|
| 配信画面 | `test` と書くと「chat OK - 名前」が数秒出る (カメラは動かさない) |
| サーバのログ | `[Chat<-] 名前: 本文` … **命令でないチャットも全部**出る (`CHAT_LOG=0` で止まる) |
| `/city` の `chat` | `received` = 生のチャット直近10件 / `recent` = 命令として通ったもの |

視聴者名は ASCII に落として描く。日本語だけの名前は落ちて `viewer` になる
(配信画面に日本語フォントが無いため。ログと `/city` には元の名前が残る)。

### 13.1 入口は1つ (`/chat`)

チャットの取り込み方は環境によって変わるので、**サーバ側の入口は1本に統一**した。

```bash
curl "localhost:8080/chat?text=focus%20rex&user=someone&token=..."
```

YouTube / Twitch / Discord / 手元の curl、どこからでも同じ形で渡せる。
`CHAT_TOKEN` を設定すると合言葉が要る (公開サーバでは必ず設定すること)。

### 13.2 YouTube に繋ぐ手順

設定は **リポジトリ直下の `.env`** に書く (`.env.example` をコピーする)。
server.js が起動時に自分で読む (依存パッケージ無し / `.gitignore` 済み)。
**既に設定されている環境変数は上書きしない**ので、Render 等のダッシュボードで
入れた値や `FOO=1 node server.js` のほうが常に優先される。

```
YT_CHAT=1
YT_API_KEY=…
YT_VIDEO_ID=…
YT_CHAT_POLL_SEC=45
```

読めていれば起動ログに `[Env] .env から N 件読み込み` と出る。

```bash
# 1) APIキーだけで読めるか試す (配信を始めてから)
node tools/yt-chat-setup.js check --key=APIキー --video=動画ID

# 2) 「APIキーだけでは足りない」と出たら OAuth のトークンを取る
node tools/yt-chat-setup.js auth --client-id=… --client-secret=…

# 3) 取れたトークンでもう一度確認
node tools/yt-chat-setup.js check --video=動画ID \
     --client-id=… --client-secret=… --refresh=…
```

Google Cloud 側の準備は「プロジェクトを作る → **YouTube Data API v3** を有効化 →
APIキーを作る」まで。OAuth が要る場合だけ、OAuth クライアント (種類は
**テレビとリミット入力デバイス**) を追加で作る。

`tools/yt-chat-setup.js` は依存パッケージ無しで動き、受け取った値を**この端末の
標準出力にしか出さない** (送信もファイル書き込みもしない)。

**アクセストークンは1時間で切れる**ので、24時間配信ではリフレッシュトークンを使う。
server.js 側が期限を見て自動で取り直す (`ytcAccessToken`)。
`YT_CHAT_TOKEN` に直接アクセストークンを入れる形は動作確認のときだけ。

`YT_VIDEO_ID` の代わりに `YT_CHANNEL_ID` を渡すと、配信中の動画を自動で探す。
ただし `search.list` は **100 units** と高いので、動画IDが分からないときだけ、
かつ5分に1回までに絞ってある。

### 13.2b 取り込みの仕組みとクォータ

公式の YouTube Data API v3 を使う:

1. `videos.list(part=liveStreamingDetails)` で `activeLiveChatId` を得る (1 unit)
2. `liveChatMessages.list` で新着を取る (**5 units/回**)

**この機能の設計を決めているのはクォータ。**

- 無料枠は **Google Cloud プロジェクトごとに 1日 10,000 units**
- リセットは**太平洋時間の深夜**。繰り越しは無い
- 使い切ると以後は `403 quotaExceeded` が返り、その日は読めない
  (`rateLimitExceeded` は別物で、こちらは短く待てば復帰する)
- 増枠は監査フォームの申請が要る (数週間〜数ヶ月・却下も多い)

単価は `videos.list` = 1、`search.list` = **100**。
`liveChatMessages.list` は公式のクォータ表で確認できなかった。多くの list は 1 unit
だが、ライブチャットは 5 unit という記述も見かけるので、**安全側の 5 を既定**にしてある
(`YT_CHAT_UNIT_COST` で直せる。見積りログにのみ効く)。5 と仮定すると:

```
10,000 / 5 = 2,000 回/日  →  43秒に1回が上限
```

そこで既定は **45秒間隔** = 指示から反映まで最大45秒。起動時に推定使用量を出し、
10,000 を超える設定なら警告する。実際の消費は Google Cloud Console の
「APIとサービス → 割り当て」で見られるので、1日回してから `YT_CHAT_UNIT_COST` と
`YT_CHAT_POLL_SEC` を詰めるとよい。

`quotaExceeded` を受け取ったら、**太平洋時間の深夜まで自動で停止**する
(叩き続けても復帰しないうえ、ログが埋まるため)。街の進行と配信は止まらない。

### 13.2d 消費量の見方

正は **Google Cloud Console → APIとサービス → YouTube Data API v3 → 割り当て**
(「Queries per day」が 10,000 の枠)。ただし反映に遅れがあるので、
サーバ側でも自前で数えている。

```bash
curl -s localhost:8080/city | python3 -c "import json,sys;print(json.load(sys.stdin)['youtube']['usage'])"
# {'ptDay':'2026-08-20', 'unitsUsed':6, 'freeQuota':10000,
#  'calls':{'videos':1,'liveChat/messages/stream':1}, ...}
```

1時間ごとにログにも出る。太平洋時間の日付が変わったらリセットする (Google と同じ区切り)。

実測 (モック): **stream 方式は繋いだ時点の 6 units から増えない**
(videos.list=1 + 接続1本ぶんの推定5)。ポーリング5秒間隔だと12秒で 16 units まで伸びた。

注意:
- `liveChat` 系の単価は非公開なので `YT_CHAT_UNIT_COST`(既定5) で計算した**推定**
- 失敗した呼び出しも数えている (Google 側も課金されうるため)
- `search.list` は 100 units。しかも **search 専用に「1日100クエリ」の別枠**がある

### 13.2c gRPC streamList (既定)

公式の本命。`youtube.googleapis.com:443` へ gRPC で繋ぎっぱなしにし、新着が push される。
**ポーリングしないので遅延はほぼゼロ、消費ユニットも接続1本ぶんだけ。**

- proto は `tools/stream_list.proto`。公式ページ掲載の `stream_list.proto` から
  **必要な部分だけ**を抜き出したもの。protobuf は知らないフィールドを読み飛ばすので
  全部書く必要はないが、**フィールド番号は公式と一致していること**
  (`display_message = 16`, `published_at = 4`, `display_name = 103`, `items = 1007`,
  `next_page_token = 100602` など。番号がズレると値が壊れる)
- サービスは `youtube.api.v3.V3DataLiveChatMessageService.StreamList`
- 認証はメタデータ。APIキーなら `x-goog-api-key`、OAuth なら `authorization: Bearer …`
- `@grpc/grpc-js` と `@grpc/proto-loader` が要る (`npm install`)。
  **入っていなければポーリングに落ちるだけ**でサーバは動く (任意ロード)
- proto-loader が snake_case を camelCase に変換するので、REST と同じ形
  (`items[].snippet.displayMessage`) で扱える = 取り込み後の処理は共通

```
YT_CHAT_MODE=auto    # 既定。gRPC が使えれば gRPC、駄目ならポーリング
YT_CHAT_MODE=grpc    # gRPC のみ
YT_CHAT_MODE=poll    # 適応ポーリングのみ
YT_CHAT_MODE=stream  # REST 版 streamList (即切断されるので実質使えない)
```

**YouTube は1接続を10秒ほどで普通に閉じてくる** (本番実測)。これは異常ではないので、
`end` (正常終了) と `error` (異常) を区別して扱う:

| 終わり方 | 扱い |
|---|---|
| `end` (サーバが普通に閉じた) | 失敗ではない。`pageToken` を持って**すぐ張り直す** |
| `error` | 失敗。2→4→8…最大60秒のバックオフ |

区別しないと、健全な接続でもバックオフが伸び続け、最後はポーリングに落ちる
(実際にそうなった: `2秒後 → 4秒後 → 8秒後 → 16秒後…`)。

張り直しの間隔は `max(YT_GRPC_RECONNECT_SEC(2秒), 予算から決まる下限)`。
`pageToken` を引き継ぐので、繋がっていない間のメッセージも次の接続で届く (取りこぼしなし)。

**履歴を捨てるのは `pageToken` を持っていない最初の接続だけ。**
張り直しのときサーバが返してくるのは「そのトークン以降 = 新着」なので、
これを毎回「履歴」として捨てると**ほとんどのコメントが消える**。
10秒ごとに切れる本番でまさにそうなった (`接続時の履歴 2 件は流さない` が延々出て、
コメントが1つも拾えない)。判定は `YTC.primed = !!YTC.pageToken`。

`pageToken` が古くて弾かれた場合 (`pageTokenInvalid` / `INVALID_ARGUMENT`) は
トークンを捨てて仕切り直す。そのままだと張り直しが延々失敗し続ける。

**接続1本あたりの単価は非公開**。既定では list と同じ 5 と仮定して予算の歯止めを掛けている
(`YT_GRPC_UNIT_COST`)。Console を1時間ほど見て消費が伸びないようなら `0` にすると
歯止めが外れ、2秒間隔で張り直し続ける = ほぼ常時接続になる。

```
YT_GRPC_UNIT_COST=5  (既定)  → 10秒接続 + 5秒待ち  … 約67%の時間つながっている
YT_GRPC_UNIT_COST=0          → 10秒接続 + 2秒待ち  … 約83%
```

keepalive (30秒ごとの ping) も明示している。grpc-js は既定で ping を打たないので、
経路上の機器やサーバ側のアイドル判定で切られやすい。

落ち方:
- **データが一度も届かないまま3回失敗** → ポーリングへ切替。
  `streamOk` は「呼び出しを作った時点」ではなく **実際にデータが届いた時点**で立てる。
  gRPC は接続前でも呼び出しオブジェクトを作れるので、そこで立てると
  「一度も繋がっていない」判定が働かず、永久に落ちてこない
- データが届いた or 5秒以上保った接続の切断は失敗として数えない
- 10回失敗が続いたらポーリングへ

### 13.2c-2 適応ポーリング (gRPC が使えないとき)

固定間隔は無駄が多い。**誰も喋っていないときに叩いても意味がない**し、
会話中に45秒待たせるのも遅い。そこで間隔を状況で決める:

```
間隔 = max( 直近に発言あり ? YT_CHAT_POLL_FAST(8秒) : YT_CHAT_POLL_SEC(45秒),
            その日の残り枠を残り時間で割った「持たせるのに必要な間隔」 )
```

3つ目の項が予算の歯止め。太平洋時間の深夜までの残り時間と残りユニットから
「このペースなら最後まで持つ」間隔を計算し、それより速くはしない。
枠を使い切って打ち止めになるより、遅くても動き続けるほうがよい。

実測 (モック / 残り5時間・単価5と仮定):

```
[YTChat] 取得間隔を 20秒に (本日の消費 約6/10,000 units)     ← 静か
[Chat<-] Synthe-Reels: test
[YTChat] 取得間隔を 9秒に (本日の消費 約16/10,000 units)     ← 会話中 (予算の歯止めが 9秒)
```

単価が実際は 1 だった場合は `YT_CHAT_UNIT_COST=1` にすると歯止めが緩み、
会話中は指定どおり 8秒 (さらに詰めれば 2秒) まで速くなる。

### 13.2d streamList を試した結果 (既定では使わない)

公式が「ライブチャットを消費する最も効率的な方法」としているのが
`liveChatMessages.streamList`。長時間つなぎっぱなしの接続に新着が push されるので、
**ポーリングが要らない = 45秒の遅延もクォータの心配も消える**。

ただし本体は **gRPC** (protobuf / `stream_list.proto`) で、素直にやると
`@grpc/grpc-js` と `.proto` が要る = 依存が増える。一方 REST 側にもクエリ仕様が
公開されているので、**まず REST の streaming エンドポイントを試し、
使えなければポーリングに自動で落ちる**形にした (依存ゼロ)。

```
YT_CHAT_MODE=poll    # 既定。適応ポーリング
YT_CHAT_MODE=stream  # streamList を試す (下記の理由で既定にはしていない)
```

**本番で試したところ、REST の streamList は「接続 → 履歴を返す → すぐ切断」を
繰り返すだけだった。** 30秒も持たず、8回で見切りをつけてポーリングに落ちた。
真のストリーミングは gRPC 版のほうで、REST 側は実質 `list` を1回叩くのと同じ挙動に見える。
張り直しのたびにユニットも食うので、**素直にポーリングしたほうが安くて速い**。

- 応答は「JSON オブジェクトが少しずつ流れてくる」形。改行区切りとは限らないので、
  括弧の深さを数えて完成したオブジェクトから取り出す (`makeJsonSplitter`)
- **接続直後の応答は「これまでの履歴」なので1回ぶんだけ捨て、以降は時刻を見ずに全部流す。**
  当初は `publishedAt < 起動時刻` で捨てていたが、**サーバの時計が YouTube 側と
  ズレていると新着まで無言で消える**。実際に本番で「接続はできるがログに何も出ない」
  状態になった
- 接続が30秒以上続いていたら、切断は失敗として数えない。
  `ytcStreamOnce` は必ず throw で終わるので、この判定が無いと健全な接続でも
  再試行カウンタが溜まり、バックオフが伸びて最後はポーリングに落ちてしまう
- 受信そのものもログに出す (`受信 321B (計… / 応答… / メッセージ…)`)。
  「繋がっているが誰も喋っていない」のか「そもそも何も来ていない」のかを切り分けるため
- 切断されたら `nextPageToken` を持ったまま張り直す (2,4,8…最大60秒のバックオフ)
- **一度も繋がらないまま 4xx** なら、その環境では使えないと判断してポーリングへ切替
- 張り直しが8回続いた場合もポーリングへ切替
- `/city` の `youtube.mode` / `pushes` / `polls` で、いまどちらで動いているか分かる

`tools/yt-chat-setup.js check` の `[4/4]` で、繋ぐ前に判定できる。

速くしたい/枠を空けたい場合の他の手:
- Google にクォータ増を申請する (監査フォーム・数週間〜数ヶ月)
- 別プロセスのチャットボットから `/chat` に流す
- gRPC 版の streamList を使う (依存を足してよければ)

`liveChatMessages.list` は OAuth が要る場合があるので、API キーに加えて
アクセストークン (`YT_CHAT_TOKEN`) も送れるようにしてある。
403/401 が返ったら `liveChatId` を捨てて取り直す。

### 13.3 安全について

**チャットの本文はデータであって命令文ではない。** 受け付けるのは
`/^!?(focus|cam|camera|watch)\s+(.{1,40})$/` に一致する形だけで、本文をそのまま
実行系に渡すことは一切しない。効果もカメラを向けることに限定してある
(街を作り直す・天気を変える・建物を建てる等はチャットからは触らせない)。
画面に出す視聴者名は `_ascii()` で ASCII に落として18文字で切る。
連投は `CHAT_COOLDOWN_SEC` で抑える。

許可する命令を増やしたいときは `handleChatCommand` の正規表現と分岐だけを足す。
