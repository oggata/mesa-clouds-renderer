# 街が変わっていく — 不可逆な蓄積の仕様 (v1)

配信を毎日見ても飽きないようにするための変更。狙いは一つ:
**「昨日と違う」を街そのものに刻む**こと。エージェントの一日は毎日同じでいい。
街のほうが変わっていれば、視聴者は見続ける理由を持つ。

対象は `server.js` (配信サーバ) のみ。`standalone/index.html` はブラウザ単体版で
sim を別実装しているが、配信していないので v1 では触らない。

**街は完成品ではなく、村から始めて育つ。** 最初は低い建物が十数軒と住民が数人だけで、
住居が建つと人が増え、人が増えると需要が生まれて店が建ち、経済が回ると背の高い建物と
大きな施設が解禁される。その全体像は **§11「街の成長」**。

---

## 0. 前提条件 — ALIGNED 世界が必須

変更前の既定は LEGACY 世界だった:

```
PASSABLE = {ROAD, BUILDING}     // 空き地(OTHER)と木(TREE)は通れない
```

つまりエージェントは**道路と建物の中しか歩かない**。空き地は一歩も踏まれないので、
「踏み跡が道になる」は LEGACY では原理的に発火しない (踏み跡ゼロ)。

ALIGNED 世界 (`WORLD_ALIGNED=1`) では:

```
PASSABLE = {ROAD, OTHER}        // 道路と空き地は通れる / 建物と木は通れない
```

`planPath` は空き地に `COST_OFFROAD`(既定4) を与えて道路優先を保つ。
つまり **「基本は道沿い、でも急ぐと空き地を突っ切る」** という、踏み跡が生まれる
のにちょうどいい条件がすでに揃っている。

### 方策の再学習は不要

`MOVE_MODE = 'pursuit'` がハードコードされているため、
**現在 ONNX 方策は移動に使われていない** (`prefetchAllActions` も pursuit なら即 return)。
移動は A* + 決定論追従。したがって「LEGACY で学習した重みが ALIGNED で壊れる」という
既存コメントの懸念は、今日の配信構成には当てはまらない。

将来 policy モードに戻すときは、ALIGNED で学習し直した重みが要る (既存の注意書き通り)。
その時も本仕様の追加分は観測を変えないので追加の制約は生まない
(**建物は既存25種からしか建てない**ので goal の25次元 one-hot も不変)。

> 決定: ALIGNED を既定にした (`WORLD_ALIGNED=0` で LEGACY に戻せる)。
> LEGACY のままなら §2 (踏み跡) だけが無効になり、他の3機能 (起業/盛衰/初回性) は動く。

### 切替時に見つかった既存バグ (修正済み)

ALIGNED で 40 体を 60 秒動かしたところ、**1体あたり到着1回**しか起きず、多くが
建物の前で足踏みしていた。原因は `stepNavigate` の到着判定:

```js
if (a.pathIdx >= a.path.length-1 && dlast < 0.8) return true;   // 建物中心まで 0.8
```

ALIGNED では建物セルに立てないので、玄関に着いた人は建物中心まで 1.0 の位置で
前進を拒否され、**永久に到着しない**。`world.js` に ALIGNED 用の
`MW.hasArrived()` (4近傍で到着) が用意されていたのに、どこからも呼ばれていなかった。
到着しなければ来客も数えられないので、本仕様の前提として先に直した。

## 1. 設計の中心 — `CITY` 恒久状態

いまワールドの状態は3か所に散らばっている:

| 変数 | 中身 | 問題 |
|---|---|---|
| `MAP` | セル種別 30×30 | `makeMap(GRID,42)` で毎回同じ |
| `BUILDING_TYPES` | `"r_c" -> typeIdx` | **buildScene が毎回振り直す** |
| `scene` のメッシュ | 描画 | 型割当と生成が同じ関数の中で癒着 |

このままだと「1軒建てるたびに全部作り直し」になり、蓄積が消える。
そこで蓄積するものを1つのオブジェクトに集約する。

```js
const CITY = {
  version: 1,
  seed: 42,                    // マップ生成 seed。合わないセーブは読まない
  grid: 30,
  dayBase: 0,                  // 起動時点までに経過したゲーム内日数 (永続)
  bornAt: 1755600000000,       // 街の誕生時刻 (実時刻ms)

  // MAP は従来どおりモジュール変数のまま (書き換えの正)。保存/復元の対象。
  // BUILDING_TYPES と cellStruct は structs から syncCity() で毎回作り直す派生表。
  //   BUILDING_TYPES … 見た目/レイキャスト用。閉店中・工事中の建物も載る
  //   「行き先に選べるか」は st.state で判定する (buildingsOfTypes / pickBuildingOfType)

  structs: [                   // 建物1軒 = 1エントリ (2x2 は左上セルが代表)
    { r:12, c:7, fp:1, typeIdx:5,
      state:'open',            // 'open' | 'construction' | 'closed' | 'gone'
      born: 0,                 // 建った日 (0 = 創世時からある)
      openedBy: null,          // 起業した住民の aid (創世建物は null)
      visits: 0,               // 累計来客
      visitsToday: 0,
      ema: 0,                  // 来客数の指数移動平均 (閉店判定に使う)
      firstCustomer: null,     // 最初の客の aid
      doneAt: null,            // 工事完了予定 (ゲーム内時刻)
    }
  ],

  foot:   Int32Array(900),     // 踏み跡カウンタ (空き地セルのみ意味を持つ)
  demand: { eat:Float32Array(900), shop:Float32Array(900),
            fun:Float32Array(900), care:Float32Array(900) },   // 需要ヒートマップ
  unmet:  { eat:0, shop:0, fun:0, care:0 },                    // 不満の積分 (カテゴリ別)

  news: [ {t, day, kind, text} ],   // 直近200件。ティッカーと /city が読む
  stats: { roadsBorn:0, shopsOpened:0, shopsClosed:0 },
};
```

### `buildScene` の分割 (最初にやる refactor)

```
planCity(map)            … 1x1/2x2 の検出と型割当。CITY が新規のときだけ呼ぶ (現行の前半)
buildScene(map, CITY)    … CITY.structs からメッシュを生成するだけ (現行の後半)
```

これで「シーンを作り直しても街は変わらない」が成立する。
さらに追加/閉店した1軒だけを差し替えられるよう、struct にメッシュ参照を持たせる
(`occluders[key+'_b'].mesh` が既にあるので、これを正として使う)。

### 部分更新の粒度

| 変更 | 再構築するもの | コスト |
|---|---|---|
| 建物 1軒 追加/閉店/取壊し | そのメッシュ1個だけ | 無視できる |
| 空き地 → 道路 | 道路/地面/摩耗のマージ済み quad メッシュ3枚 | 900 quad ≒ 1ms、1日1回 |
| トレイル | 触らない | — |

建物は元から**個別メッシュ**で描かれている (近接フェードのため)。
`mergeGeos` は道路と地面の板だけ。したがって「1軒足すと全部作り直し」問題は実は
存在せず、道路の板だけ差分更新すればいい。

## 2. 機能A — 踏み跡が道になる

### 測る
`stepAll()` の前進成功地点 (`a.visited` を更新している所) で:

```js
if (MAP[r][c] === OTHER) CITY.foot[r*GRID+c]++;
```

道路の上の足跡は数えない (既に道なので情報がない)。

### 見せる (連続)
踏み跡は**閾値を超える前から見えている**必要がある。ある日突然アスファルトが
生えるより、土が露出していく方が「蓄積」に見える。

地面 quad を3枚のマージ済みメッシュに分ける:

| 段階 | 条件 | 色 |
|---|---|---|
| 草地 | それ以外 | `0x9ccc65` (現行) |
| 踏み固め | 踏み跡のある空き地の**上位20%** かつ `foot ≥ WEAR_1` | `0xa8a878` |
| 露出 | **上位5%** かつ `foot ≥ WEAR_2` | `0xb9a97e` |

**絶対数ではなく上位%で塗る**。300体では1分で 500 踏みに達したので、絶対閾値だと
人数しだいで空き地が一面茶色になる。上位%なら常に「いちばん踏まれている一部」だけが
土になり、道の生まれる筋がそのまま見える。`WEAR_1/WEAR_2` は下限として残す
(できたばかりの街で数踏みの差を土扱いしないため)。

再構築は道が増えたときは即座に、踏み跡の濃淡は 20 秒ごと (最短3秒間隔)。

### 昇格する (離散・1日1回)
毎日のロールオーバー (§6) で:

1. 候補 = `MAP[r][c]===OTHER` かつ **4近傍に ROAD がある**セル
2. `foot` 降順でソート
3. 上位から最大 `ROAD_PER_DAY`(既定2) 本を `ROAD` に昇格。ただし `foot >= FOOT_MIN`(既定 300)
4. 昇格したセルの `foot` は 0 に戻し、周囲8セルの foot を 1.5倍する
   (道は道を呼ぶ = 商店街が線状に伸びる)
5. 昇格しなかったセルは `foot *= FOOT_DECAY`(既定 0.9)
   — 一度の横断が何週間もかけて積み上がって全面道路になるのを防ぐ

**なぜ閾値ではなく日次ランキングか**: エージェント1000体・1体あたり毎秒3セル進むので、
絶対閾値は agent 数と TICK に強く依存して調整不能になる。「今日いちばん踏まれた空き地を
2本だけ道にする」なら、規模が変わっても1日の変化量が一定に保たれ、配信の
「毎朝2本ずつ道が伸びる」というリズムにもなる。

### 副作用
- `MAP` を書き換えるので `planPath` / `PASSABLE` / FPV レイキャストが自動的に追従する
- 道路を**足す**変更なので連結性は悪化しない (分断の心配は §3 の建築側だけ)
- ニュース: `🛣 空き地に道ができた (12,7)` — 出しすぎると安いので1日1件に集約

## 3. 機能B — 足りないものを住民が起業する

### 3.1 「足りない」を測る
需要 = **不満 × 距離の積分**。`stepNeeds()` (1Hz) の中で、欲求が閾値を超えている
エージェントについて:

```js
const n = needOf(a);                       // 'eat' | 'shop' | 'bored' | 'sick' のみ対象
const cat = NEED_TO_CAT[n];                // eat/shop/fun/care
const d = nearestDist(a, CAT_IDX[cat]);    // 最寄りの該当建物までのチェビシェフ距離
const w = clamp((d - D_OK) / (D_FAR - D_OK), 0, 1);   // D_OK=4, D_FAR=14 セル
CITY.unmet[cat] += w * dtSec;
CITY.demand[cat][cell(a)] += w * dtSec;    // どこで不満だったか
```

- 最寄りが `D_OK` 以内なら需要ゼロ。**近くにあるのに空腹**は供給不足ではない
- 該当建物が街に1軒も無ければ `w = 1`
- `nearestDist` は該当カテゴリの建物リストの線形走査。対象は「欲求が高い人」だけなので
  最悪 1000体 × 60軒 = 60k回/秒。既存の孤独判定 (1000² = 100万回/秒) より軽い

### 3.2 どこに建てるか
`CITY.demand[cat]` が「未充足の欲求を抱えた人が通った回数」のヒートマップになっている。

候補セル:
- `MAP[r][c] === OTHER` かつ 4近傍に `ROAD` がある (= 道に面している)
- **閉店した建物の跡地** (§4) は候補に優先的に含める。連結性チェックが不要で、
  跡地が再利用されるのは絵として強い
- 建てても**連結性が壊れない**こと (下記)

スコア = `demand[cat][cell]` + 近傍3×3の demand の平均 × 0.5。最大のセルを選ぶ。

§2 と組み合わさると **道ができる → 人が通る → 店ができる → さらに人が通る** が回る。
放っておくと商店街が創発するはず。これが本仕様のいちばん面白いところ。

### 3.3 連結性ガード (必須)
空き地を建物にすると、そこが唯一の通路だった場合に街が分断される。
`world.js` に道具が揃っているので、それを使う:

```js
const before = countPassable(MW.largestComponent(MW.passableMask(map, WORLD)));
map[r][c] = BUILDING;
const after  = countPassable(MW.largestComponent(MW.passableMask(map, WORLD)));
if (after !== before - 1) { map[r][c] = OTHER; /* この候補は捨てて次へ */ }
```

「最大連結成分がちょうど1セルだけ減った」= 誰も孤立していない。
BFS 1回 = 900セル、1日1回なので無視できるコスト。

さらに `MW.ensureAllBuildingsReachable` で「新しい建物に玄関があるか」も担保する。

### 3.4 何を建てるか
**既存25種の footprint=1 のみ**。方策の goal は25次元 one-hot なので、種類を増やさない
限り再学習は不要 (2x2 は4セル必要 + 連結性が壊れやすいので v1 では建てない)。

その結果、起業できるのは実際には次の8種になる:

| カテゴリ | 建てられる業種 |
|---|---|
| eat | 屋台 / ラーメン / 牛丼 / カフェ / 弁当 |
| shop | コンビニ / 商店 |
| care | 薬局 |
| fun | **なし** (競技場・神社・博物館・図書館は全部 2x2) |

`fun` は需要としては測るが起業対象外。2x2 の建設を入れるのが v2 の宿題。

カテゴリ内での種類選択は**近傍の希少性**で決める:
半径8セル以内に同タイプが少ないものを優先。同じ通りにラーメン屋が3軒並ぶのを防ぐ。

### 3.5 誰が建てるか
`personas.json` に `enterprise` (0..1, 既定 0.3) を追加する。

```json
{ "id":"D", "name":"Businessman Cole", "color":"#ffee00", "enterprise":0.8 }
{ "id":"B", "name":"Homebody Lily",    "color":"#00ccff", "enterprise":0.05 }
```

起業者 = `argmax(enterprise × そのカテゴリへの自分の不満寄与)`。
つまり「自分が一番困っていて、かつ性格的に動く人」。決定論なので再現できる。

副作用 (ここが**不可逆**の本体):
- `a.work = [r,c]`、`a.owns = [r,c]` — その住民の一日のルーチンが以後ずっと変わる
- `assignHomes()` は `a.owns` があれば `a.work` を上書きしない
- 店主は営業時間 (9-17時) に自分の店にいるので、店の周りに常に人がいる絵になる

### 3.6 発火の抑制 (飽和対策)

当初は「不満の総和 ÷ 供給軒数」を圧として使う設計だったが、**実測で常にゼロに潰れた**。
この街は 900セルに 139軒と密で、どのカテゴリも最寄りが 2〜3セル以内にあり、
「遠くて満たせない」人がほとんど居ないため。総和で見るかぎり永久に発火しない。

そこで発火条件を**場所ごと**に変えた:

```
score(cell) = demand[cat][cell]*2 + Σ(3x3 近傍の demand)*0.5     // agent-秒
発火 = max_cell score / (DAY_MINUTES*60) >= FOUND_SITE           // agent-day 単位
```

意味は「何人日ぶんの『遠くて満たせない欲求』がその一角を通ったか」。
街全体では足りていても、**一帯にだけ飲食店が無い**状況は拾える。
そして開店すればその一帯の人は `D_OK` 以内に店を持つので需要の流入が止まり、
飽和は自動的に収まる (グローバルな供給密度で割る必要がない)。

**1日あたり最大1件**。起業したら `unmet[cat] *= 0.4` に加えて、
**新しい店の周囲3セルの需要ヒートマップをゼロにする**。開店後は新たな需要が積もらない
一方で、過去に積んだ熱は減衰待ちで残るため、消さないと同じ場所が数日連続で最大スコアに
なり隣に同種の店が建ち続ける (実測: 2日で薬局2軒)。

実測値 (300体 / `DAY_MINUTES=2` / 既定閾値):

| 日 | eat | care |
|---|---|---|
| Day1 | 0.00 (最寄り平均 —) | 0.02 (4.1セル・遠い61%) |
| Day3 | 0.20 (2.5セル・遠い34%) | 0.28 (5.7セル・遠い89%) |

減衰 0.75 の平衡は日次流入の約4倍なので、この規模で 0.5〜0.8 に落ち着く見込み。
**本番 (1000体) はこの3倍前後**になるので、`FOUND_SITE=0.5` なら序盤は毎日1軒建ち、
街が埋まるにつれて自然に止まる。速すぎ/遅すぎならログの数字を見て調整する。

`FOUND_SITE` の既定 0.5 は暫定値。毎日のログに全カテゴリの score と
「最寄り平均距離 / 遠い割合」が出るので、1〜2日回してから決めること:

```
[City] 起業の圧 eat:0.12(39軒 最寄り平均2.1c 遠い3%) shop:0.44(20軒 ...) | 発火 0.5 agent-day
```

### 3.7 建つ / なくなる の演出

街の形が変わる瞬間は**必ず見せる**。人を追うカメラを一時的に止めて現場に寄り、
建物を動かし、画面に一言出す。

| できごと | 建物の動き | カメラ | 画面の一言 |
|---|---|---|---|
| 着工 | 工事の箱が地面から**せり上がる** | 現場に寄って回り込む (既定9秒) | 「カフェ の工事が始まりました」 |
| 開店 | 本体が地面から**せり上がる** | 同上 | 「Mika #1 の カフェ が建ちました」 |
| 閉店 | シャッター (色が沈む) | 同上 (7秒) | 「Cole #4 の 薬局 が閉店しました」 |
| 取り壊し | 建物が地面に**沈む** | 同上 | 「薬局 がなくなりました」 |

**地面より下は自然に隠れる。** 地面は W×W の不透明プレーン (z=0) で、カメラは常に
その上にあるので、`position.z` を下げるだけで「地中から出てくる / 地中に潜る」になる。
クリッピング平面は要らない。動きは ease-out で最後にふわっと止まる。

**アニメはカメラが着いてから動かす。** イベントは待ち行列に並ぶので、状態が変わった
瞬間に動かすと「カメラが到着したころには沈み終わっている」ことになる (実際になった)。
`showCityEvent(r, c, 一言, 秒数, {st, kind})` に渡すと、開始位置に置くところまでを
即座に行い、実際の動き出しはカメラがその場所に着いた時刻に合わせる。

**取り壊しは沈みきってから地面を書き換える。** 先に空き地にすると、まだ建物が
立っているのに人がすり抜けて見える。`state='demolishing'` の間は通行不可のままで、
アニメの完了コールバックで `MAP` とメッシュと一覧をまとめて片付ける。

一言は3D映像に焼き込むので YouTube 側にも出る (ティッカーとは別枠。ティッカーは
一周に時間がかかるので、その瞬間に見せたいものはバナーで出す)。

### 3.8 工事中の状態
即座にポップさせない。

1. 起業決定時: `MAP[r][c] = BUILDING`、struct を `state:'construction'` で追加。
   状態が `open` でないので誰も目的地に選ばない
2. 灰色の低い箱がせり上がる (§3.7)
3. `CONSTRUCTION_HOURS`(既定2ゲーム時間) 後に完成 → 本体がせり上がる
4. 最初の客が入ったら `firstCustomer` を記録してニュース (§5 と合流)

落ちている間に完成予定時刻を過ぎた建物は、起動時に開業済みとして扱う。
「住民が建てた店」は `st.founded` で区別する (初日に建った店は `born=0` で、
創世からある建物と見分けが付かなかった)。

## 4. 機能C — 店の盛衰

### 数える
到着地点 (`a.trips++` があった所) に `onArrive(a, dest)` を差し込む:

```js
const st = structAt(dest[0], dest[1]);
if (st) { st.visits++; st.visitsToday++; ... }
```

LEGACY/ALIGNED どちらでも到着イベントは同じ場所で起きるので分岐不要。

### 閉店
日次ロールオーバーで、**起業で建て直せる業種だけ**を対象に
(閉店しうる集合 = §3.4 の8種。潰れたきり二度と建たない業種を作らないため):

```
ema = ema*0.7 + visitsToday*0.3
```

閉店条件 (すべて満たす1軒だけ、1日最大1件):
- `state === 'open'`
- 築 `GRACE_DAYS`(既定3日) 以上 — 建ったばかりの店に猶予を与える
- `ema` が最下位、かつ `ema < 同業の ema 平均 × CLOSE_FRAC`(既定 0.25)
  — 絶対値だとエージェント数で意味が変わって調整不能になる (踏み跡を日次ランキングに
  したのと同じ理由)。「同業と比べて客が来ていない店」なら規模に依存しない。
  中央値ではなく平均なのは、店数が多いと半数以上が来客ゼロで中央値が 0 になり、
  条件が永久に成立しなくなるため。来客が均等なら平均の 25% を割る店が無くなり、
  閉店は自然に止まる (= 偏っている間だけ淘汰が起きる)
- そのカテゴリの営業中店舗数が `MIN_PER_CAT`(既定2) より多い — 飲食店が全滅しない

**住宅/職場/病院/学校/駅/市役所は閉店しない。**
自宅が消えると `assignHomes` の割当が壊れるし、病院が消えると病気が治らなくなる。
「潰れるのは店だけ」なら倫理的な据わりの悪さも一切ない。

閉店処理:
- `types` から削除 (誰も目的地に選ばなくなる)
- マテリアルを暗くする (`color.multiplyScalar(0.45)`) = シャッター表現。
  専用テクスチャを用意するならここを差し替えるだけ
- セルは `BUILDING` のまま = 連結性は変わらない
- ニュース: `🚪 ラーメン屋 (12,7) が閉店しました`

### 取り壊し → 空き地
`DEMOLISH_DAYS`(既定5日) 閉店したままなら `MAP[r][c] = OTHER` にしてメッシュを削除。
空き地に戻るので、また誰かが建てられる。連結性は改善方向なのでチェック不要。

これで **建物のレベルで生死が回る**。lifegame の生成消滅を、人ではなくインフラでやる形。

## 6. 機能E — 画面に出す (Day カウンタ / ティッカー)

### 日付の定義
`gameHour()` は起動時刻からの実時間で計算している。同じ式で日を出す:

```js
const elapsedDays = (START_HOUR + elapsed*24/(DAY_MINUTES*60)) / 24;
gameDay() => CITY.dayBase + Math.floor(elapsedDays);
```

`dayBase` を永続化するので、再起動しても Day は戻らない。
`gameDay()` の値が変わった瞬間に **`dailyRollover(day)`** を1回だけ呼ぶ
(踏み跡昇格 / 起業判定 / 閉店判定 / `visitsToday` リセット / demand 減衰 をここに集約)。

朝5時に切り替わるように `+ 5/24` のオフセットを入れる — 深夜に街が変わるより
「朝起きたら道ができている」ほうが配信の絵として自然。

### HUD 描画パス
YouTube に出ているのは 3D をそのまま rawvideo にしたフレームで、文字は一切乗っていない。
そこで描画を2パスにする:

```js
renderer.autoClear = false;
renderer.render(scene, mainCam);
renderer.clearDepth();
renderer.render(hudScene, hudCam);   // OrthographicCamera(-W/2, W/2, H/2, -H/2)
```

文字のラスタライズは **SVG → sharp → DataTexture**。`buildNeedIcons()`
で既に実績のある方法なので新しい依存は要らない。

| 要素 | 位置 | 更新頻度 |
|---|---|---|
| `DAY 47  08:32` / `POP 34  TOWN  SUNNY` | 左上 (250×54) | 最短1秒に1回 |
| `CAM  Explorer Rex #1` / `hungry - Ramen Shop` | 右上 (300×46) | 最短1秒に1回 |
| ニュースティッカー | 下端の帯 (高さ30) | ニュース追加時にテクスチャ再生成、スクロールは板の x を動かすだけ |
| できごとのバナー | 上寄り中央 (高さ48) | イベント発生時のみ数秒 |

**焼き込む文字は ASCII だけにする。** 本番 (Linux) に日本語フォントが無く、
日本語を描くと全部豆腐になった。そこで HUD だけ英語にし、
ログ / `/city` / WebSocket は日本語のままにしてある。
そのために `news(kind, 日本語, 英語)` の3引数目と、建物名の英語表 `BLDG_EN`、
発展段階の `en` (HAMLET/VILLAGE/TOWN/CITY/METROPOLIS) を持っている。

漏れを防ぐ仕掛けを2段構えで入れてある:

1. **`_ascii()` で描画直前に非 ASCII を落とす**(日付板・ティッカー・バナーの3か所)。
   何かが混ざっても豆腐にはならず、その文字が消えるだけで済む
2. **`en` を持たないニュースはティッカーに流さない**。英語化する前に保存された街を
   復元すると、`data/city_state.json` の中の記録は日本語しか持っていない。
   そのまま描くと復元直後だけ豆腐が流れるので、英語のある記録だけを選ぶ
   (記録自体は残るので `/city` とログでは日本語で読める)

天気はティッカーに流さない (日付板に常時出ているうえ、変化が多くて街のできごとを
押し出してしまう)。`TICKER_SKIP` で除外している。

**いま何を映しているか**は右上に常時出す (`hudCamLines`)。誰を追っているのか
分からないまま眺めることになるのを避けるため。表示は4通り:

| 状況 | 表示 |
|---|---|
| 住民を追跡 | `CAM Explorer Rex #1` / `hungry - Ramen Shop` (一人称なら `eye view -` が付く) |
| チャット指名 | `CAM Explorer Rex #1` / `requested by <視聴者名>` |
| 街のできごと | `CAM city event` / `Ramen Shop was built` |
| 俯瞰 | `CAM overview` / `the whole town` |

### 6.1 ティッカーの中身 — できごと と 住民の様子

開店/閉店だけだと事件の連続で、人が住んでいる感じが出ない。そこで
`LIFE_NEWS_SEC`(既定25秒) ごとにランダムな住民を1人選び、いまの様子を流す。

```
D5  Ramen Shop opened - run by Cole #11   *   Lily #2 is sleepy and heading home
    *   D5 Footpaths turned into 2 new roads   *   Rex #3 fell ill and is heading to a Pharmacy
```

- **街のできごとと住民の様子は別の枠**に貯めて、ティッカーで**交互に**並べる。
  同じ列に入れると、1日数件しかない開店/閉店が、数十秒ごとに出る住民の様子に
  押し出されてしまう。住民の様子は保存もしない (街の記録ではなく、その瞬間の景色)
- 抽選は状態で重み付けする (病気6 / 空腹3 / 退屈2 / 買い物2 / 睡眠1 / 勤務1)。
  一様抽選だと夜は「寝ている」ばかりになる
- 直近に出した住民は避け、さらに**名前と数字を伏せた「文の形」**が直近3件と
  重ならないよう数回引き直す。小さな村では全員が同じ状態 (勤務時間帯など) になり、
  名前だけ違う同じ文が並んでしまうため
- 言い回しは各状態に2〜3種類。勤務中は空腹/眠気を一言添える
  (`is on the way to work (already getting hungry)`)
- 3回に1回ほどは状態ではなく**来歴**を流す
  (`has been to 7 different kinds of places in town` / `runs the Ramen Shop in this town`)
- `/city` の `residents` で日本語と英語の両方を確認できる

ティッカーは幅2048pxのテクスチャを持つ板を毎フレーム左へ流す。ortho カメラの視錐台の外は
そのまま切られるのでクリッピング処理は不要。

`HUD=0` で無効化できるようにする (負荷が問題になったとき、あるいは
OBS 側で別途オーバーレイを入れたくなったとき用)。

### ブラウザ側
ブラウザ視聴者が見る JPEG も同じ描画結果なので、HUD はそのまま映る。
client.html 側に二重表示しない。ただし他の用途 (OBS のオーバーレイ、外部ダッシュボード)
のために `statsLoop` の WebSocket メッセージへ `day` と直近ニュース5件を足してある。

## 7. 永続化

`data/city_state.json` (`CITY_STATE_FILE` で変更可)。

- 保存: 60秒ごと + `SIGINT`/`SIGTERM` (既存の `shutdownYt` のハンドラに相乗り)
- 読込: 起動時。`version` と `seed` と `grid` が一致しなければ**読まずに新規生成**
  (マップ生成則を変えたときに壊れた街を復元しないため)
- サイズ見積り: structs 300 × 100B + foot/demand 900×5 + agents 1000×(aid,mask,owns)
  ≒ 200KB。JSON で十分
- `newmap` コマンドと `/city?reset=1` は CITY を破棄して作り直す (= 街の作り直し)

> ⚠️ **デプロイ先のディスクが永続かどうかの確認が要る。**
> Render の標準インスタンスはファイルシステムが揮発性で、再デプロイのたびに消える。
> その場合は永続ディスクをマウントするか、外部ストレージ (S3 等) に置くか、
> あるいは「プロセスが生きている間だけ蓄積する」と割り切るかの判断が必要。
> 蓄積が数時間で消えるなら本仕様の狙い (1週間ぶりの視聴者が別の街を見る) は達成できない。

## 10. 詰まりそうな箇所 (実装時に確認済み)

1. **`BUILDING_TYPES` の再生成** — buildScene が呼ばれるたび型が振り直されていた。
   `planStructures` に切り出して創世時のみに変更 (これをやらないと以降すべてが無意味)。
2. **到着判定** — ALIGNED では玄関で到着としないと、誰も店に着かない (§0)。
3. **連結性** — 空き地を建物にする前に `canBuildAt()` で最大連結成分を比較し、
   「ちょうど1セルだけ減る」ことを確認する。減り方が違えばその候補は捨てる。
4. **`assignHomes()` の再呼び出し** — `a.owns` があれば職場を上書きしない。
   起業した住民の職場が `reset` で元に戻らないようにするため。
5. **エージェント1000体** — `NUM_AGENTS` が `CAM_INTERVAL_MS` から読まれていて既定
   1000体になっている (server.js の書き間違いと思われる)。日次処理は O(セル数)、
   毎秒処理は O(agents × カテゴリ内軒数) に収めてある。
   ※ 別件だが `updateOcclusionFade()` が O(agents × occluders) を毎フレーム回している。
     1000体だと毎フレーム約60万回で、ここが一番重い。本仕様とは独立の既存課題。
6. **飽和** — 場所ベースの発火にしたので、開店するとその一帯の需要が止まって自然に収まる。
   それでも `FOUND_PER_DAY=1` の上限は残してある。
7. **ティッカーの安さ** — 「道ができた」は1日1件に集約。初回性ニュースは
   `FIRST_NEWS_COOLDOWN` で間引き、新店の初客・開業・閉店を優先する。
8. **日本語フォント** — ティッカーは sharp(librsvg) で描くので、Linux では
   `fonts-noto-cjk` が無いと豆腐になる。起動時に自己診断して警告を出す。

## 11. 街の成長 — 村から始めて育てる

「建物が建っていく様子」を見せるには、最初から完成した街があってはいけない。
そこで**村から始めて、人口と経済で育てる**。

### 11.1 フィールドそのものが小さく始まって広がる

マップ配列は `GRID`(30) 四方のままだが、**実際に世界として使うのは中央の
`CITY.size` 四方だけ**。外側は `VOID`(=4) にして、通行不可・描画なし・レイを止める。
地面の板もフィールドのぶんしか敷かないので、**街は宙に浮いた島**のように見え、
広がると島が大きくなる。

`makeMap` は 0〜3 しか返さないので、`VOID` は実行時にだけ現れる4つ目の種別。
**マップ生成には一切手を入れていない**ので学習側 (mesa_env) との bit 一致は保たれる。

最初は `START_SIZE`(既定10) 四方。土地が足りなくなったら1日1回、両側1セルずつ広がる:

```
拡張する条件 = 建て込み具合 > EXPAND_DENSITY(0.28)  または  空き区画 ≤ EXPAND_FREE(6)
```

**空き区画の数だけで判断してはいけない。** 建物が増えるほど「建物に接した空き地」も
増えるので、その数はなかなか減らず、いつまでも広がらなくなる。建て込み具合
(フィールドに占める建物セルの割合) を主な判断に使う。

新しく現れる土地は草地で、元の地形の木を `EXPAND_TREES`(既定3セルに1本) に間引いて
少しだけ生やす。一面の林にすると「建物が無くて木だけの場所」になってしまうため。
拡張の瞬間は引きの画で「街の範囲が広がりました (14×14)」と出す。

### 11.1b 最初の建物

生成された「完成した街」に対する後処理として間引く (`villageStart`)。

- フィールドの外は `VOID`、中の建物はいったん全部さら地に
- フィールド内で中心に近い区画を `START_BUILDINGS`(既定12) だけ選び、
  **1x1 の低い建物**として建て直す (元の建物跡を優先し、足りなければ道に面した空き地から補う)
- 用途は下の順に割り当てる。**生活に必要なものから先に揃う**ように並べてある:

```
house, house, post, kiosk, house, ramen, conbini, house, cafe, pharmacy,
house, bento, shop, house, gyudon   (以降くり返し)
```

12軒なら 住宅5 / 職場1 (郵便局) / 飲食4 (屋台・ラーメン・カフェ・弁当) / コンビニ1 / 薬局1。
**住む場所・働く場所・食べる場所は必ず入る。**

- 人口は `START_POP`(既定8) から。住居5軒 = 定員10 なので最初から全員に家がある

`START_VILLAGE=0` で従来の「完成した街」から始められる。

### 11.2 人口 — 家が建つと人が増える

**家が無い人は生まれない。** 人口の上限は**住居の定員**で決まり、
`growPopulation` は空きベッドのぶんしか転入させない。

| 建物 | 定員 |
|---|---|
| 🏠 住宅 | `HOUSE_CAP` = 2 |
| 🏬 マンション | `APT_CAP` = 12 (高さ2.1なので「町」から解禁) |

毎日、定員に空きがあるぶんだけ転入する:

```
転入数 = min(空き, MOVEIN_MAX(8), ceil(人口 × POP_GROWTH(0.15)))
```

住居が `HOME_PRESSURE`(0.85) を超えて埋まると、翌朝いちばん優先して住宅が建つ。
建てた家は工事 (2ゲーム時間) を挟むので、**定員が増えるのは翌日**。
人口は常に定員の少し下を追いかける形になる。

実測 (1日=1分の加速設定):

| 日 | 人口 / 定員 |
|---|---|
| Day2 | 10 / 12 |
| Day3 | 12 / 12 ← 満室 → 住宅を建てる |
| Day5 | 14 / 26 ← マンションが建って一気に増える |
| Day9 | 26 / 26 ← 満室 → また建てる |
| Day10 | 30 / 38 |

家なし 0人、定員超過の家 0軒 を `/city` で確認済み。

万一あふれた場合 (保存データの設定を変えた等) の受け皿も用意してある:
- 割当は**いちばん空いている家**へ (先頭の家に全員詰め込まない)
- 家の無い住民は最寄りの住居で休める (`pickLifeGoal` / `stepNeeds`)。
  これが無いと疲労が 1.0 で飽和したまま永久に徘徊する
- `/city` の `population.homeless` と起動ログの `⚠ 家なし` で観測できる
同じく勤め人が職場の定員 (`WORK_CAP`=6 × 職場数) の `WORK_PRESSURE`(0.9) を超えると
職場が建つ。**建設の優先順位は 住むところ → 働くところ → 商売**。生活の器のほうが先。

1日に建てられる軒数は人口に比例する (`1 + 人口/FOUND_PER_POP`、最大6)。
人が増えるほど街が速く育つ = 複利で伸びる。

拠点の割当 (`assignHomes`) は**既に住んでいる人をそのまま**にして空きへ入れる方式に
変えた。以前は index で機械的に割り当てていたので、家が1軒建つたびに全員の住所がずれ、
「引っ越してきた」が成立しなかった。

### 11.3 発展段階 — 経済が回ると高い建物が解禁される

経済活動 = **店/施設への来店の累計** (`CITY.econ`)。これが溜まると段階が上がり、
建てられる建物の**高さの上限**と **2x2 の可否**が緩む。

| 段階 | 高さ上限 | 2x2 | 経済 | 解禁されるもの (例) |
|---|---|---|---|---|
| 集落 | 1.4 | — | 0 | 住宅 / 郵便局 / 屋台 / コンビニ / カフェ / 薬局 |
| 村 | 1.7 | — | 400 | 銀行 |
| 町 | 2.1 | ✓ | 2,000 | マンション / スーパー / 神社 / 学校 / 駅 / 図書館 / 病院 / 市役所 |
| 市 | 2.6 | ✓ | 8,000 | オフィス / 博物館 / 競技場 / 複合ビル |
| 都市 | 3.3 | ✓ | 25,000 | タワー |

`ECON_SCALE` で発展の速さをまとめて調整できる (小さいほど早い)。

**業種は「街にいちばん少ないもの」から建つ。** 解禁された新種は必ず0軒なので、
段階が上がった瞬間にそれが建つ = 街が育つほど建物の種類が増えていく。
方策の goal は BLDG_TYPES(25) の one-hot のままなので**再学習は不要**。
変わるのは「いつ建つか」だけ。

段階が上がった瞬間は、引きの画で街全体を映して
「この街は 町 になりました」と出す (§3.7 の演出に `wide` オプションを追加)。

### 11.4 2x2 の建設

「町」以降は 2x2 が解禁されるので、`pickSite` は footprint 対応にした。

- `blockFree(r,c,fp)` … fp×fp が全部空き地か
- `facesRoadOrBuilding(r,c,fp)` … 道か既存の建物に接しているか
  (村のうちは道が中心にしか無いので「建物の隣」も許さないと街が広がれない)
- `canBuildFootprint(r,c,fp)` … 建てても最大連結成分が **ちょうど fp×fp セルしか
  減らない**か = 誰も孤立しないか

### 11.5 回っている輪

```
住居が建つ → 人が増える → 需要が増える → 店が建つ → 来店が増える
   ↑                                                      ↓
   └────── 住居が足りなくなる ←── 経済が回る ←── 段階が上がる ──┘
                                    (高い建物 / 大きい施設が解禁)
```

これに §2 の「踏み跡が道になる」が重なると、
**道ができる → 人が通る → そこに店が建つ → さらに人が通る**
も同時に回る。放っておくと商店街と道路網が勝手に育つ。

## 13. 配信チャットからの指示

視聴者が「このキャラを映して」と書くと、数秒だけそのキャラを追う。

```
test / ping         → 画面に「chat OK - <視聴者名>」と数秒出る (疎通確認)
!focus rex          → Explorer Rex #1 を 10秒追う
focus Lily #2       → 表示名で指定
focus B             → ペルソナ id で指定
focus 3             → 3人目
focus overview      → 俯瞰
focus random        → ランダム
```

画面には `Camera: Explorer Rex #1 (by <視聴者名>)` と数秒出る。
**自分の名前が配信に出る**のが、この機能のいちばんの価値だと思う。

カメラの優先順位は **チャットの指名 > 街のできごと > 自動切替**。
指名は数秒なので、その間に起きた着工/取り壊しは待ち行列で待ち、明けてから再生される
(アニメもカメラ到着に合わせて始まるので、見逃しにはならない)。

### 13.0b 届いているかの確認

チャットが**そもそも届いているのか**、届いたが**命令として解釈されなかった**のかは
別の話なので、3か所で見られるようにしてある。

| 見る場所 | 内容 |
|---|---|
| 配信画面 | `test` と書くと「chat OK - 名前」が数秒出る (カメラは動かさない) |
| サーバのログ | `[Chat<-] 名前: 本文` … **命令でないチャットも全部**出る (`CHAT_LOG=0` で止まる) |
| `/city` の `chat` | `received` = 生のチャット直近10件 / `recent` = 命令として通ったもの |

視聴者名は ASCII に落として描く。日本語だけの名前は落ちて `viewer` になる
(配信画面に日本語フォントが無いため。ログと `/city` には元の名前が残る)。

### 13.1 入口は1つ (`/chat`)

チャットの取り込み方は環境によって変わるので、**サーバ側の入口は1本に統一**した。

```bash
curl "localhost:8080/chat?text=focus%20rex&user=someone&token=..."
```

YouTube / Twitch / Discord / 手元の curl、どこからでも同じ形で渡せる。
`CHAT_TOKEN` を設定すると合言葉が要る (公開サーバでは必ず設定すること)。

### 13.2 YouTube に繋ぐ手順

設定は **リポジトリ直下の `.env`** に書く (`.env.example` をコピーする)。
server.js が起動時に自分で読む (依存パッケージ無し / `.gitignore` 済み)。
**既に設定されている環境変数は上書きしない**ので、Render 等のダッシュボードで
入れた値や `FOO=1 node server.js` のほうが常に優先される。

```
YT_CHAT=1
YT_API_KEY=…
YT_VIDEO_ID=…
YT_CHAT_POLL_SEC=45
```

読めていれば起動ログに `[Env] .env から N 件読み込み` と出る。

```bash
# 1) APIキーだけで読めるか試す (配信を始めてから)
node tools/yt-chat-setup.js check --key=APIキー --video=動画ID

# 2) 「APIキーだけでは足りない」と出たら OAuth のトークンを取る
node tools/yt-chat-setup.js auth --client-id=… --client-secret=…

# 3) 取れたトークンでもう一度確認
node tools/yt-chat-setup.js check --video=動画ID \
     --client-id=… --client-secret=… --refresh=…
```

Google Cloud 側の準備は「プロジェクトを作る → **YouTube Data API v3** を有効化 →
APIキーを作る」まで。OAuth が要る場合だけ、OAuth クライアント (種類は
**テレビとリミット入力デバイス**) を追加で作る。

`tools/yt-chat-setup.js` は依存パッケージ無しで動き、受け取った値を**この端末の
標準出力にしか出さない** (送信もファイル書き込みもしない)。

**アクセストークンは1時間で切れる**ので、24時間配信ではリフレッシュトークンを使う。
server.js 側が期限を見て自動で取り直す (`ytcAccessToken`)。
`YT_CHAT_TOKEN` に直接アクセストークンを入れる形は動作確認のときだけ。

`YT_VIDEO_ID` の代わりに `YT_CHANNEL_ID` を渡すと、配信中の動画を自動で探す。
ただし `search.list` は **100 units** と高いので、動画IDが分からないときだけ、
かつ5分に1回までに絞ってある。

### 13.2b 取り込みの仕組みとクォータ

公式の YouTube Data API v3 を使う:

1. `videos.list(part=liveStreamingDetails)` で `activeLiveChatId` を得る (1 unit)
2. `liveChatMessages.list` で新着を取る (**5 units/回**)

**この機能の設計を決めているのはクォータ。**

- 無料枠は **Google Cloud プロジェクトごとに 1日 10,000 units**
- リセットは**太平洋時間の深夜**。繰り越しは無い
- 使い切ると以後は `403 quotaExceeded` が返り、その日は読めない
  (`rateLimitExceeded` は別物で、こちらは短く待てば復帰する)
- 増枠は監査フォームの申請が要る (数週間〜数ヶ月・却下も多い)

単価は `videos.list` = 1、`search.list` = **100**。
`liveChatMessages.list` は公式のクォータ表で確認できなかった。多くの list は 1 unit
だが、ライブチャットは 5 unit という記述も見かけるので、**安全側の 5 を既定**にしてある
(`YT_CHAT_UNIT_COST` で直せる。見積りログにのみ効く)。5 と仮定すると:

```
10,000 / 5 = 2,000 回/日  →  43秒に1回が上限
```

そこで既定は **45秒間隔** = 指示から反映まで最大45秒。起動時に推定使用量を出し、
10,000 を超える設定なら警告する。実際の消費は Google Cloud Console の
「APIとサービス → 割り当て」で見られるので、1日回してから `YT_CHAT_UNIT_COST` と
`YT_CHAT_POLL_SEC` を詰めるとよい。

`quotaExceeded` を受け取ったら、**太平洋時間の深夜まで自動で停止**する
(叩き続けても復帰しないうえ、ログが埋まるため)。街の進行と配信は止まらない。

### 13.2d 消費量の見方

正は **Google Cloud Console → APIとサービス → YouTube Data API v3 → 割り当て**
(「Queries per day」が 10,000 の枠)。ただし反映に遅れがあるので、
サーバ側でも自前で数えている。

```bash
curl -s localhost:8080/city | python3 -c "import json,sys;print(json.load(sys.stdin)['youtube']['usage'])"
# {'ptDay':'2026-08-20', 'unitsUsed':6, 'freeQuota':10000,
#  'calls':{'videos':1,'liveChat/messages/stream':1}, ...}
```

1時間ごとにログにも出る。太平洋時間の日付が変わったらリセットする (Google と同じ区切り)。

実測 (モック): **stream 方式は繋いだ時点の 6 units から増えない**
(videos.list=1 + 接続1本ぶんの推定5)。ポーリング5秒間隔だと12秒で 16 units まで伸びた。

注意:
- `liveChat` 系の単価は非公開なので `YT_CHAT_UNIT_COST`(既定5) で計算した**推定**
- 失敗した呼び出しも数えている (Google 側も課金されうるため)
- `search.list` は 100 units。しかも **search 専用に「1日100クエリ」の別枠**がある

### 13.2c gRPC streamList (既定)

公式の本命。`youtube.googleapis.com:443` へ gRPC で繋ぎっぱなしにし、新着が push される。
**ポーリングしないので遅延はほぼゼロ、消費ユニットも接続1本ぶんだけ。**

- proto は `tools/stream_list.proto`。公式ページ掲載の `stream_list.proto` から
  **必要な部分だけ**を抜き出したもの。protobuf は知らないフィールドを読み飛ばすので
  全部書く必要はないが、**フィールド番号は公式と一致していること**
  (`display_message = 16`, `published_at = 4`, `display_name = 103`, `items = 1007`,
  `next_page_token = 100602` など。番号がズレると値が壊れる)
- サービスは `youtube.api.v3.V3DataLiveChatMessageService.StreamList`
- 認証はメタデータ。APIキーなら `x-goog-api-key`、OAuth なら `authorization: Bearer …`
- `@grpc/grpc-js` と `@grpc/proto-loader` が要る (`npm install`)。
  **入っていなければポーリングに落ちるだけ**でサーバは動く (任意ロード)
- proto-loader が snake_case を camelCase に変換するので、REST と同じ形
  (`items[].snippet.displayMessage`) で扱える = 取り込み後の処理は共通

```
YT_CHAT_MODE=auto    # 既定。gRPC が使えれば gRPC、駄目ならポーリング
YT_CHAT_MODE=grpc    # gRPC のみ
YT_CHAT_MODE=poll    # 適応ポーリングのみ
YT_CHAT_MODE=stream  # REST 版 streamList (即切断されるので実質使えない)
```

**YouTube は1接続を10秒ほどで普通に閉じてくる** (本番実測)。これは異常ではないので、
`end` (正常終了) と `error` (異常) を区別して扱う:

| 終わり方 | 扱い |
|---|---|
| `end` (サーバが普通に閉じた) | 失敗ではない。`pageToken` を持って**すぐ張り直す** |
| `error` | 失敗。2→4→8…最大60秒のバックオフ |

区別しないと、健全な接続でもバックオフが伸び続け、最後はポーリングに落ちる
(実際にそうなった: `2秒後 → 4秒後 → 8秒後 → 16秒後…`)。

張り直しの間隔は `max(YT_GRPC_RECONNECT_SEC(2秒), 予算から決まる下限)`。
`pageToken` を引き継ぐので、繋がっていない間のメッセージも次の接続で届く (取りこぼしなし)。

**履歴を捨てるのは `pageToken` を持っていない最初の接続だけ。**
張り直しのときサーバが返してくるのは「そのトークン以降 = 新着」なので、
これを毎回「履歴」として捨てると**ほとんどのコメントが消える**。
10秒ごとに切れる本番でまさにそうなった (`接続時の履歴 2 件は流さない` が延々出て、
コメントが1つも拾えない)。判定は `YTC.primed = !!YTC.pageToken`。

`pageToken` が古くて弾かれた場合 (`pageTokenInvalid` / `INVALID_ARGUMENT`) は
トークンを捨てて仕切り直す。そのままだと張り直しが延々失敗し続ける。

**接続1本あたりの単価は非公開**。既定では list と同じ 5 と仮定して予算の歯止めを掛けている
(`YT_GRPC_UNIT_COST`)。Console を1時間ほど見て消費が伸びないようなら `0` にすると
歯止めが外れ、2秒間隔で張り直し続ける = ほぼ常時接続になる。

```
YT_GRPC_UNIT_COST=5  (既定)  → 10秒接続 + 5秒待ち  … 約67%の時間つながっている
YT_GRPC_UNIT_COST=0          → 10秒接続 + 2秒待ち  … 約83%
```

keepalive (30秒ごとの ping) も明示している。grpc-js は既定で ping を打たないので、
経路上の機器やサーバ側のアイドル判定で切られやすい。

落ち方:
- **データが一度も届かないまま3回失敗** → ポーリングへ切替。
  `streamOk` は「呼び出しを作った時点」ではなく **実際にデータが届いた時点**で立てる。
  gRPC は接続前でも呼び出しオブジェクトを作れるので、そこで立てると
  「一度も繋がっていない」判定が働かず、永久に落ちてこない
- データが届いた or 5秒以上保った接続の切断は失敗として数えない
- 10回失敗が続いたらポーリングへ

### 13.2c-2 適応ポーリング (gRPC が使えないとき)

固定間隔は無駄が多い。**誰も喋っていないときに叩いても意味がない**し、
会話中に45秒待たせるのも遅い。そこで間隔を状況で決める:

```
間隔 = max( 直近に発言あり ? YT_CHAT_POLL_FAST(8秒) : YT_CHAT_POLL_SEC(45秒),
            その日の残り枠を残り時間で割った「持たせるのに必要な間隔」 )
```

3つ目の項が予算の歯止め。太平洋時間の深夜までの残り時間と残りユニットから
「このペースなら最後まで持つ」間隔を計算し、それより速くはしない。
枠を使い切って打ち止めになるより、遅くても動き続けるほうがよい。

実測 (モック / 残り5時間・単価5と仮定):

```
[YTChat] 取得間隔を 20秒に (本日の消費 約6/10,000 units)     ← 静か
[Chat<-] Synthe-Reels: test
[YTChat] 取得間隔を 9秒に (本日の消費 約16/10,000 units)     ← 会話中 (予算の歯止めが 9秒)
```

単価が実際は 1 だった場合は `YT_CHAT_UNIT_COST=1` にすると歯止めが緩み、
会話中は指定どおり 8秒 (さらに詰めれば 2秒) まで速くなる。

### 13.2d streamList を試した結果 (既定では使わない)

公式が「ライブチャットを消費する最も効率的な方法」としているのが
`liveChatMessages.streamList`。長時間つなぎっぱなしの接続に新着が push されるので、
**ポーリングが要らない = 45秒の遅延もクォータの心配も消える**。

ただし本体は **gRPC** (protobuf / `stream_list.proto`) で、素直にやると
`@grpc/grpc-js` と `.proto` が要る = 依存が増える。一方 REST 側にもクエリ仕様が
公開されているので、**まず REST の streaming エンドポイントを試し、
使えなければポーリングに自動で落ちる**形にした (依存ゼロ)。

```
YT_CHAT_MODE=poll    # 既定。適応ポーリング
YT_CHAT_MODE=stream  # streamList を試す (下記の理由で既定にはしていない)
```

**本番で試したところ、REST の streamList は「接続 → 履歴を返す → すぐ切断」を
繰り返すだけだった。** 30秒も持たず、8回で見切りをつけてポーリングに落ちた。
真のストリーミングは gRPC 版のほうで、REST 側は実質 `list` を1回叩くのと同じ挙動に見える。
張り直しのたびにユニットも食うので、**素直にポーリングしたほうが安くて速い**。

- 応答は「JSON オブジェクトが少しずつ流れてくる」形。改行区切りとは限らないので、
  括弧の深さを数えて完成したオブジェクトから取り出す (`makeJsonSplitter`)
- **接続直後の応答は「これまでの履歴」なので1回ぶんだけ捨て、以降は時刻を見ずに全部流す。**
  当初は `publishedAt < 起動時刻` で捨てていたが、**サーバの時計が YouTube 側と
  ズレていると新着まで無言で消える**。実際に本番で「接続はできるがログに何も出ない」
  状態になった
- 接続が30秒以上続いていたら、切断は失敗として数えない。
  `ytcStreamOnce` は必ず throw で終わるので、この判定が無いと健全な接続でも
  再試行カウンタが溜まり、バックオフが伸びて最後はポーリングに落ちてしまう
- 受信そのものもログに出す (`受信 321B (計… / 応答… / メッセージ…)`)。
  「繋がっているが誰も喋っていない」のか「そもそも何も来ていない」のかを切り分けるため
- 切断されたら `nextPageToken` を持ったまま張り直す (2,4,8…最大60秒のバックオフ)
- **一度も繋がらないまま 4xx** なら、その環境では使えないと判断してポーリングへ切替
- 張り直しが8回続いた場合もポーリングへ切替
- `/city` の `youtube.mode` / `pushes` / `polls` で、いまどちらで動いているか分かる

`tools/yt-chat-setup.js check` の `[4/4]` で、繋ぐ前に判定できる。

速くしたい/枠を空けたい場合の他の手:
- Google にクォータ増を申請する (監査フォーム・数週間〜数ヶ月)
- 別プロセスのチャットボットから `/chat` に流す
- gRPC 版の streamList を使う (依存を足してよければ)

`liveChatMessages.list` は OAuth が要る場合があるので、API キーに加えて
アクセストークン (`YT_CHAT_TOKEN`) も送れるようにしてある。
403/401 が返ったら `liveChatId` を捨てて取り直す。

| `CHAT_FOCUS_SEC` | 10 | 1回の指名で映す秒数 |

### 13.2e 視聴者が街に参加する

| コマンド | 効果 |
|---|---|
| `!join` / `!join Hikari` | **視聴者がこの街の住民になる**。名前を持った住民が引っ越してくる |
| `!cheer <名前>` | 住民を応援する。退屈が晴れ、応援数が住民に貯まる |

**`!join` は街の決まりを曲げない。** 家が空いていなければ**入居待ちの列**に入り、
住宅が建った翌朝に順番で迎えられる (`growPopulation` が待機列を先に消化する)。
「家が無い人は生まれない」という原則を視聴者にも適用することで、
「自分の家が建つのを待つ」という見る動機が生まれる。

- 名前は ASCII のみ (配信画面が ASCII しか描けないため)。日本語だけの表示名だと
  空になってしまうので、**`!join Hikari` のように自分で指定できる**逃げ道を用意した
- 同名は `#2` を付けて回避。2文字未満と NG ワード (`CHAT_NG_WORDS`) は拒否
- 視聴者住民は人口の `VIEWER_MAX_FRAC`(既定30%) まで
- 同じ人がもう一度 `!join` すると、その住民にカメラが寄る (「自分を映して」になる)
- **保存される**。再起動しても名前と応援数はそのまま (`savedAgents` に `n`/`v`/`b`/`c`)

`!cheer` の効果は「退屈が晴れる」= 既存の「人と関わった」と同じ扱いなので、
街の理屈を壊さない。応援数は来歴としてティッカーに流れ
(`Hikari has been cheered 12 times by viewers`)、カメラ表示にも `[12 cheers]` と出る。

`/city` の `viewers` で 住民一覧 / 入居待ち / 人気者 が見られる。

### 13.2f 住民が「行きつけ」を覚える / 視聴者が教える

住民は AI で動いている、という前提を視聴者に体験させるための仕組み。
**勾配学習ではなく、場所ごとの評価をオンラインで更新する**もの
(方策の ONNX には触れないので再学習は不要)。

```
目的地の点数 = -距離 + PREF_WEIGHT × その住民のその店への好み
好みの更新    = 行った結果 (近かったか / 混んでいたか) で移動平均
```

数日で「Rex はいつもあのカフェ」という**習慣**ができ、店の盛衰が経路依存になる。
**自宅と職場は覚えない** (割り当てられた場所であって選んだ場所ではないため。
これを外すと `likes House x4` のような無意味な行きつけができる)。

| コマンド | 効果 |
|---|---|
| `!teach <住民> <業種>` | その住民にいちばん近い同業の店を勧める |
| `!ask <住民>` | その住民が何を覚えたかを見せる |

**推薦はできるが命令はできない。** 勧められた店には次の用事で必ず一度行くが、
定着するかは本人の経験しだい。`TEACH_DAYS`(既定3日) 後に判定して結果を流す:

```
[News] 💡 oggata が Explorer Rex #1 に 🍜 ラーメン屋 (15,13) を勧めた
[Learn] Explorer Rex #1 は勧められた ramen (15,13) へ向かう
[Learn] Explorer Rex #1 が勧められた店に到着 (15_13)
[News] Explorer Rex #1 は結局いつもの店に戻った (oggata のおすすめは定着せず)
```

思い通りにならないのが肝。定着すれば `⭐ oggata のおすすめが Rex の行きつけになった`。

**口コミ**: すれ違った住民同士が「行きつけ」を少しだけ共有する
(`stepNeeds` の孤独判定ループに相乗りしているので追加コストはほぼゼロ)。
誰かの推薦が広まると `🗣 oggata のおすすめが 10人に広まった` と流れる。
視聴者1人の行動が街全体の経済に効く因果が見える。

好みは日次で少し減衰する (`PREF_DECAY`)。保存は住民ごとに上位6件まで。

| 名前 | 既定 | 意味 |
|---|---|---|
| `PREF_WEIGHT` | 6 | 目的地選びで好みをどれだけ効かせるか |
| `PREF_LEARN` | 0.35 | 1回の経験でどれだけ更新するか |
| `PREF_DECAY` | 0.97 | 好みの日次減衰 |
| `TEACH_DAYS` | 3 | 定着したか判定するまでの日数 |
| `GOSSIP_P` | 0.02 | すれ違いで好みが伝わる確率/秒 |
| `NEED_HI` | 0.62 | 欲求で目的地を選ぶ閾値 (小さいほど住民がよく動く) |

### 13.2g 使い方を配信画面から伝える

概要欄を読まない視聴者にも届くよう、`CHAT_HINT_EVERY`(既定6) 回に1回、
住民の様子の代わりに操作ヒントをティッカーに流す。

```
TYPE IN CHAT:  !focus rex  - the camera follows that resident for 10s
TYPE IN CHAT:  !join  - move into this town as a resident
```

`CHAT_HINT_EVERY=0` で無効。文面は `CHAT_HINTS` にある。

### 13.3 安全について

**チャットの本文はデータであって命令文ではない。** 受け付けるのは
`/^!?(focus|cam|camera|watch)\s+(.{1,40})$/` に一致する形だけで、本文をそのまま
実行系に渡すことは一切しない。効果もカメラを向けることに限定してある
(街を作り直す・天気を変える・建物を建てる等はチャットからは触らせない)。
画面に出す視聴者名は `_ascii()` で ASCII に落として18文字で切る。
連投は `CHAT_COOLDOWN_SEC` で抑える。

許可する命令を増やしたいときは `handleChatCommand` の正規表現と分岐だけを足す。

## 14. 街の変化の速さ (`CITY_TEMPO`)

配信を見ている人が退屈しないためには、建つ/なくなるが**目に見える頻度**で起きる必要がある。
関係するパラメータは道・起業・閉店・取り壊しに散らばっているので、
**まとめて効く倍率**を1つ用意した。個別に env 指定した値にもこの倍率が掛かる。

| | TEMPO=1 (以前の既定) | **TEMPO=2 (現在の既定)** | TEMPO=4 |
|---|---|---|---|
| 1日に増える道 | 2本 | 4本 | 8本 |
| 道になる踏み跡の下限 | 300 | 150 | 75 |
| 起業の発火 (agent-day) | 0.5 | 0.25 | 0.125 |
| 何人につき1日1軒 建つか | 40 | 20 | 10 |
| 1日の閉店数 | 1 | 2 | 4 |
| 開業から閉店判定までの猶予 | 3日 | 2日 | 1日 |
| 閉店の基準 (同業平均比) | 25% | 50% | 90% |
| 閉店から取り壊しまで | 5日 | 3日 | 1日 |

`MIN_PER_CAT` (カテゴリごとに残す最低軒数) だけは倍率を掛けない。安全弁なので。

実測 (TEMPO=2 / 人口10〜23の村): ほぼ毎日 `建設+1` があり、`閉店+1` `取壊+1` `道+1` が
数日おきに入る。TEMPO=1 では建設が数日に1回で、閉店はもっと稀だった。

### 14.1 人流が店の生死に効く

「人が通らない場所の店は潰れる」を入れた。閉店判定に使う健全度は:

```
健全度 = 来客の指数移動平均(ema) + FOOT_HEALTH × 周囲3x3の踏み跡
```

同業の健全度の平均と比べて `CLOSE_FRAC` を下回る店が閉店する。
`FOOT_HEALTH=0` にすると従来どおり「来た客の数」だけで決まる。

これで **道ができる → 人が通る → その店が生き残る / 通らない店が潰れる**
という因果が閉じる。`/city` の `atRisk` に各店の `health` と `footNear` が出るので、
どちらが効いているか確認できる。

## 15. 密集して動けなくなる問題 (本番40日目)

配信を40日ほど回したところ、**建物が密集して住民が移動できない**状態になった。
原因は3つ重なっていた。

### 15.1 何が起きていたか

**1. 立地スコアが塊を作っていた**

`siteScoreGeneric` が「隣接する建物1つにつき +6」を与えていた。虫食いを防ぐつもりが、
建物が建つほどその隣が高得点になり、**塊が育つ正のフィードバック**になっていた。

**2. 住宅と職場に撤去の道が無かった**

閉店の対象は `CLOSABLE_CATS`(eat/shop/fun/care) だけで、**住宅と職場は閉店も
取り壊しもされない**。人口が増えると住宅と職場は増え続け、減ることが一度も無い。
40日ぶん積み上がれば埋まって当然だった。

**3. 建設に上限が無かった**

フィールドは `EXPAND_DENSITY` を超えると広がるが、**30x30 (GRID) に達したらそれ以上
広がれない**。それでも建設は止まらないので、密度は上がる一方になる。

さらに `canBuildFootprint` は「最大連結成分が分断されないこと」しか見ていない。
**幅1の通路だらけでも「連結」なので通ってしまう。** 通れる*広さ*を見る指標が必要だった。

### 15.2 通行性 (walkability)

```
walkability = 通行可能セルの「4近傍のうち通れる数」の平均 / 4
```

1 に近いほど広々。実測では、生成直後の街 (建物139軒・密度0.21) で **0.68**。
これを基準に `WALK_MIN=0.55` を下限とした。

建設時の判定に3つ足した:

| 判定 | 目的 |
|---|---|
| `wouldChoke(r,c,fp)` | 置いた後、**通れる隣が1以下のセル**を作らない = 行き止まりと幅1通路を防ぐ |
| `openRatio(r,c) >= MIN_OPEN_RATIO`(0.35) | すでに詰まっている一帯には建てない |
| `density < BUILD_MAX_DENSITY`(0.42) かつ `walkability >= WALK_MIN` | 街全体が詰まったら建設自体を止める |

立地スコアも変えた。隣接ボーナスは残しつつ **2軒までで頭打ち、4軒以上は減点**、
さらに `openRatio` を加点に入れて「開けた場所」を好むようにした。

**効果 (ストレステスト)**: 240回の強制建設に対し、受け付けられたのは32軒だけ。
密度は 0.214 → 0.25 で頭打ちになり、通行性は 0.679 → 0.653 で止まった。
**街が自分で自分の首を絞められなくなった。**

### 15.3 住宅と職場にも撤去の道を作る

- `markVacant()` … 誰も住んでいない住宅 / 誰も働いていない職場が
  `VACANT_DAYS`(4日) 続いたら閉じる → 通常の取り壊し待ち行列に乗る。
  **住んでいる家は絶対に壊さない。** 各カテゴリ2軒は必ず残す
- `relieveCongestion()` … `walkability < WALK_MIN` のとき、
  **いちばん道を塞いでいる建物を1日1軒**畳む (使われていないものだけ)

これで住宅と職場も「増えるだけ」ではなくなった。

### 15.4 すでに詰まった街を助ける

1日1軒では40日ぶんの詰まりは解けないので、手動の一括整理を用意した。

```bash
curl -s "localhost:8080/city?force=declutter&n=20"
curl -s localhost:8080/city | python3 -c "import json,sys;print(json.load(sys.stdin)['field'])"
```

道をいちばん塞いでいる建物から順に n 軒畳む。**使われている住居と職場は対象外**なので、
全部埋まっている街では少ししか減らないことがある (その場合は人口が多すぎる)。

実装上の注意: 沈むアニメが終わるまで `MAP` は建物のままなので、
**先に n 軒ぶんの対象を選んでから**まとめて沈める (選びながら壊すと2軒目以降が
「まだ塞がっている」前提で選ばれる)。また一括時はカメラを動かさない
(20軒ぶんのカメライベントを積むと配信が3分間ジャックされる)。

### 15.5 パラメータ

| 名前 | 既定 | 意味 |
|---|---|---|
| `WALK_MIN` | 0.55 | これを下回ると建設を止め、取り壊しを始める |
| `BUILD_MAX_DENSITY` | 0.42 | 建物セルの割合の上限 |
| `MIN_OPEN_RATIO` | 0.35 | 5x5窓に残すべき通行可能セルの割合 |
| `VACANT_DAYS` | 4 | 空き家/空き職場を畳むまでの日数 |

`/city` の `field` に `walkability` と `buildingPaused` が出る。
建設が止まっているときは `buildingPaused: true`。

## 16. 描画コスト — フィールドが広がるほど重くなる問題

街が育つとフレーム時間が伸びていた。`PERF_LOG=1` で1フレームを
「agent更新 / 遮蔽フェード / 描画 / 読出 / JPEG」に分解して計測したところ、
効いていたのは **テクスチャの大きさではなくメッシュ数 (= ドローコール数)** だった。

### 16.1 計測 (住民300人・フィールド30×30・建物139軒)

| | 変更前 | メッシュ整理後 | 住民インスタンシング後 |
|---|---|---|---|
| メッシュ数 | 5,561 | 658 | **352** |
| ドローコール (概算) | 約1,100 | 約1,100 | **約490** |
| テクスチャ実体 | 96 | **24** | 24 |
| 描画 | 13.7ms | 5.2ms | **3.3ms** |
| 遮蔽フェード | 4.7ms | **0.4ms** | 0.6ms |

見た目は変えていない (建物のテクスチャの向き・住民の造形・足跡の色すべて同一)。
住民には後から歩行アニメを足した (§16.5)。

### 16.2 内訳と対策

**(a) 足跡が 3,000 メッシュ** — 住民300人 × `MAX_TRAIL`=10。
ジオメトリとマテリアルは共有できていたが、ドローコールは共有できない。
→ 全住民の足跡を **1メッシュの中の板の集まり** に変更。住民ごとに `MAX_TRAIL` 枚の
スロットを固定で割り当て、リングバッファで上書きする。ペルソナごとの色は
頂点カラーで持つ。未使用スロットは4頂点を同じ点に潰す (縮退三角形 = 描画されない)。
`Trail` / `initTrailField` / `addTrail` / `clearTrails`。

**(b) 住民1人が 8 メッシュ** — 脚2・胴・肩・首・頭・髪・鼻。
しかも **ジオメトリとマテリアルを人数分だけ新規生成** していた (300人なら約2,400ジオメトリ)。
部位は一切アニメーションせず常に一体で動くだけなので、
ジオメトリを1本にマージして全住民で共有し、色が固定の肌・髪・ズボンは
頂点カラーに焼き込んだ。体の色だけは住民ごとに変わるのでマテリアルを分ける
(色ごとにキャッシュ = ペルソナ数ぶんだけ)。
→ 1人 = **1メッシュ / 2ドローコール**、ジオメトリは街全体で1個。
`mergeGeos` / `agentGeometry` / `createAgentMesh`。

**(c) 建物の側面テクスチャを面ごとに clone** — 面の向きを揃えるために
`texture.clone()` して `rotation` / `repeat` を設定していた。clone した Texture は
three.js から見て別物なので **同じ画像が4回GPUに載る** (24種 → 96実体)。
→ 向きの補正を **ジオメトリの UV に焼き込む** ことで、1種1枚に統一した。
併せて側面4面を1グループにまとめ、地面に接していて見えない底面は描かないようにした。
→ 建物1軒あたり **6 → 2 ドローコール**。`bakeBoxUV`。

**(d) 遮蔽フェードが O(住民 × 遮蔽物)** — 毎フレーム全住民と全建物・全木を突き合わせていた。
→ 遮蔽物をセルでバケツ分けし、住民の周囲だけを見る。`occluderGrid`。

### 16.3 共有リソースの破棄に注意

(b)(c) で **ジオメトリ・マテリアル・テクスチャを全体で共有** するようになったため、
シーンを作り直すとき (`newmap` / `/city?reset=1` / フィールド拡張) に
`disposeScene` が共有物を壊すと、以後の建物が真っ白になったり住民が消えたりする。
共有するものには印を付け、破棄対象から外している。

- ジオメトリ: `SHARED_GEO` (Set) に登録
- マテリアル / テクスチャ: `userData.shared = true`

建物のテクスチャ (`texCache`) は起動時に1ファイル1枚だけ読む。
`buildingMatCache` はシーンごとに作り直すが、参照している Texture は共有のまま残す。

### 16.4 住民のインスタンシング

上の (b) で住民1人 = 1メッシュ (2ドローコール) まで減らしたが、300人なら
**600ドローコール**が残る。住民は形がみな同じで、違うのは
「位置・向き・体の色・歩行の位相」だけなので、`InstancedMesh` 2本
(体 / 肌・髪・ズボン) にまとめて **2ドローコール** で描くようにした。

- 体だけ住民ごとに色が変わるので、ジオメトリを「体」と「それ以外」に分け、
  体側は `setColorAt` のインスタンスカラーで塗る。
- 住民1人ぶんの位置と向きは `THREE.Object3D` の器 (`agentMeshes[i]`) に持たせる。
  ジオメトリもマテリアルも持たず scene にも入れない、純粋な変換だけの入れ物。
  `renderLoop` がここに補間後の値を書き、`syncAgentInstances` がまとめて
  インスタンス行列へ流し込む。屋内の住民はスケール0の行列で消す。
- `initAgentInstances` / `setAgentColor` / `syncAgentInstances`。

**three 0.132 の落とし穴**: `color_fragment` は `USE_COLOR` /
`USE_COLOR_ALPHA` のときしか `vColor` を使わない。`USE_INSTANCING_COLOR` だけだと
頂点シェーダで計算した色がフラグメントで捨てられ、**全員白**になる
(後のバージョンで修正されている)。体マテリアルにも `vertexColors: true` を立てて
経路を通し、白の頂点カラーの上に `instanceColor` を掛けさせている。

**欲求アイコン** (`NEED_ICONS=1`) は住民に親子付けできなくなったので、
scene 直付けにして毎フレーム頭上へ置き直す形に変えた。

### 16.5 歩行アニメーション — ボーンを使わない理由

住民を歩かせたいが、ボーン (`SkinnedMesh`) は**負荷を下げる仕組みではない**。

- ドローコールは減らない。1体1コールのまま。
- 頂点ごとに最大4本のボーン行列をブレンドするので、頂点あたりの計算が増える。
- スケルトンは共有できないので、住民ごとにボーン行列の更新が要る。
  これは §16 でまさに潰した「1体ごとの固定費」そのもの。
- three.js r132 に `InstancedSkinnedMesh` は無いので、§16.4 と排他になる。

本番の Linux VPS では headless-gl がソフトウェア描画になり、頂点シェーダの仕事が
そのまま CPU 時間になるため、スキニングのペナルティはさらに大きい。

そこで**頂点シェーダで歩行サイクル**を作った。住民ごとの歩行位相と振幅を
インスタンス属性 `aWalk = (位相, 振幅)` で渡し、脚の付け根 (`AGENT_HIP`) より
下の頂点だけを付け根まわりに前後へ振る。左右の脚はローカル x の符号で逆位相にする。
肌・髪・ズボンのジオメトリの中で `AGENT_HIP` より下にあるのは脚だけなので、
高さの比較だけで脚を選び出せる。`addWalkShader`。

- **位相は「実際に進んだ距離」で進める**ので、歩幅と速さが自然に一致する
  (時間で進めると、止まっていても脚が動く/速く歩いても歩幅が変わらない)。
- **振幅は止まると 0 に落ちる**ので、立ち止まっている住民の脚は止まる。
  屋内に入った住民も 0 にする。

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `WALK_CYCLE` | `CELL*0.30` | 1歩行周期で進む距離 |
| `WALK_FULL` | `CELL*0.018` | 振幅が最大になる1フレームの移動量 |
| `WALK_SWING` | `0.55` | 脚の振れ角 (rad) |

`PERF_LOG=1` の行末に `歩行124/300(平均振幅0.22)` が出る。
歩行シェーダが実際に駆動されているかの確認用。

### 16.6 共有リソースの破棄に注意 (再掲)

住民のジオメトリ・マテリアルも全体で共有しているので、§16.3 と同じく
`SHARED_GEO` と `userData.shared` で `disposeScene` の対象から外している。
シーンを作り直す3か所 (`newmap` / `/city?reset=1` / 起動時) では
`initTrailField` と `initAgentInstances` を必ず呼び直すこと。

### 16.7 まだ残っている手

- 建物を種類ごとに `InstancedMesh` にまとめる (352 → 150程度)。
  ただし1軒単位のせり上がり/沈み込みアニメと遮蔽フェードが効かなくなるので、
  アニメ中・フェード中の建物だけ通常メッシュに逃がす作りが要る。
- 木も同様にインスタンス化できる (現状205メッシュ)。こちらは遮蔽フェードだけが問題。
- `MAX_TRAIL` を下げる (足跡は1メッシュになったのでメッシュ数には効かない。
  頂点数だけの問題になった)。

## 17. 配信の動画IDが変わっても追いかける

配信を立て直すと YouTube の動画IDが変わる。以前は `.env` の `YT_VIDEO_ID` を
手で書き換えるまでチャットが死んだままだった。

- ポーリングが `liveChatEnded` を受けても `chatId` しか捨てておらず、
  **死んだ動画IDを永久に掴み続けていた**。
- 再探索は `YT_CHANNEL_ID` を設定している場合しか走らず、
  設定していなければ復帰の手段が無かった。

### 17.1 直したこと

**(a) チャンネルIDを自分で学習する** — `YT_CHANNEL_ID` が未設定でも、いま持っている
動画IDから `videos.list(part=snippet)` で投稿チャンネルを引く (1 unit)。
**配信が健全なうちに**一度だけ学習しておく。配信が切れてから学習しようとすると、
手がかりの動画IDを既に捨てていて間に合わない (実装中に一度踏んだ)。
`ytcEnsureChannel`。

**(b) 死んだ動画IDを捨てる** — ポーリングが `liveChatEnded` / `liveChatNotFound` /
`liveChatDisabled` / 404 を返したら、`chatId` だけでなく**動画IDごと**捨てて
次の配信を探しにいく。`ytcInvalidateVideo`。

**(c) 安く探す** — `search.list` は **100 units** と高い (5分おきに叩くと1日28,800
units で無料枠を超える)。代わりにアップロード一覧をたどる:

| | 呼び出し | units |
|---|---|---|
| 1 | `channels.list(part=contentDetails)` → uploads プレイリストID | 1 |
| 2 | `playlistItems.list(part=contentDetails)` → 直近5件の動画ID | 1 |
| 3 | `videos.list(part=liveStreamingDetails, id=カンマ区切り)` | 1 |

**合計 3 units**。ライブ配信もアップロード一覧に載るのでこれで拾える。
反映が遅れて載っていない場合の保険として `search.list` を残してあるが、
1日 `YT_SEARCH_MAX_PER_DAY` (既定10) 回までに制限している。

**(d) 見つけたIDを保存する** — `data/yt_live.json` に動画IDと学習済みチャンネルIDを
書く。再起動しても探し直さなくて済む。
`YT_VIDEO_ID` を明示している場合はそちらを優先する (手で指定したものを勝手に
上書きしない)。その値が死んでいれば (a)(b)(c) で数 units 使って復帰する。

### 17.2 使い方

```
curl http://localhost:8080/yt              # いまの動画ID / チャンネルID / チャット状態
curl "http://localhost:8080/yt?refind=1"   # いますぐ探し直す
node tools/yt-chat-setup.js find --key=API_KEY --video=前の動画ID
```

`.env` でチャンネルIDを明示しておくと、学習の 1 unit すら要らない:

```
YT_CHANNEL_ID=UCxxxxxxxxxxxxxxxxxxxxxx
```

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `YT_AUTO_FIND` | 有効 | `0` で自動追従を切る |
| `YT_SCAN_RECENT` | 5 | アップロード一覧を何件見るか |
| `YT_SEARCH_MIN_SEC` | 120 | 探索の最短間隔 (秒) |
| `YT_ALLOW_SEARCH` | 有効 | `0` で search.list のフォールバックを使わない |
| `YT_SEARCH_MAX_PER_DAY` | 10 | search.list の1日あたり上限 |
| `YT_LIVE_FILE` | `data/yt_live.json` | 見つけた動画IDの保存先 |

### 17.3 検証

モックAPI (実APIのレスポンス形状に合わせたもの) で確認した:

- 起動時に `YT_VIDEO_ID` が死んでいる → チャンネル学習 → 新しい動画を発見 →
  チャット再開。`search.list` は 0 回、合計 10 units。
- **配信中に動画IDが変わる** (`liveChatEnded`) → 約15秒で新しい動画へ乗り換え。
  連続2回の立て直しでも追従した。
- サーバ再起動後、保存済みの動画IDから復帰。

実APIでの唯一の未確認点は「ライブ配信がアップロード一覧に**すぐ**載るか」。
載らないチャンネル/タイミングがあれば `search.list` のフォールバックが拾う。
一度 `node tools/yt-chat-setup.js find` を実配信に対して実行して確かめておくとよい。

### 17.4 一人称カメラの目線の高さ

`FPV` の目の高さが `Math.max(CELL*0.5, CELL*0.66*CHAR_SCALE)` になっていて、
下限のほうが常に勝っていた。`CHAR_SCALE=1/3` だと住民の実際の頭の高さは
`CELL*0.22` なので、**実際の目線の2倍以上**から見下ろす画になっていた。
下限を外して実高をそのまま使い、`FPV_EYE` (既定 1.0) で倍率を調整できるようにした。

## 18. 住民どうしのコミュニケーション (social.js)

住民は以前から3セル以内の他人を感知していて、`gossip()` で「行きつけ」を
交換していた。しかし**画面上は何も起きず、ティッカーにも出ず、関係も残らない**。
すれ違いざまに数値を交換しているだけだった。

ここでは (1) 関係グラフ (2) 見える立ち話 (3) 話題 を足す。

### 18.1 なぜ別ファイルなのか

`server.js` は既に大きい。街の物理は `world.js`、人間関係は `social.js` に分ける。
`social.js` は `world.js` と同じく**純粋なモジュール**で、`server.js` の
グローバルを一切参照しない。呼ぶ側が `ctx` (コールバックの束) を渡す。

| | social.js | server.js |
|---|---|---|
| 誰と誰が会ったか (`a.rel`) | ○ | |
| 立ち話の状態機械 (`a.talk`) | ○ | |
| 話題を**決める** | ○ | |
| 近接判定の空間ハッシュ | ○ | |
| 話題が街に**効く** (好みの伝播) | | ○ |
| 描画・カメラ・ニュース | | ○ |

好みの機構 (`pref` / `prefBump` / `gossip`) は既に server.js にあるので、
二重には持たない。social.js は「何を話すか」を決めて呼び戻すだけ。

### 18.2 関係グラフ

`a.rel = { 相手aid: {n:会った回数, s:親密度 0..1, d:最後に会った日} }`。

- 親密度は `s += relGain * 相性 * (1-s)`。相性は `personas.json` の
  `sociability` から決まる (Social Marco 0.95 / Homebody Lily 0.10)。
- 1人が覚えていられるのは `relMax` (既定12) 人まで。溢れたら一番薄い相手を忘れる。
- 会わない日が続くと日次で `relDecay` 倍に薄れ、0.02 を切ると忘れる。
- `relFriend` (既定0.5) を越えたら友人。`CITY.stats.friendships` に積む。

**片側だけ trimRel で捨てられると双方向の親密度がズレる。**
「両方が同時に閾値を越えたら友人」にすると人口が多い街では永久に成立しないので、
どちらかが越えた時点で成立させ、`_f` 印で二重発火を防いでいる。

### 18.3 混雑への上限 — ここが一番の落とし穴だった

本番は `NUM_AGENTS=6000`。密集した場所では半径3セルに数百人居るので、
近傍を全部見ると **1tick で 246,000 ペア** になった (実測)。

対策は「人混みの中で全員に挨拶はしない」を素直に実装すること:

- `neighbors()` に `limit` を渡して、見つかった時点で打ち切る
- 1tick に視界へ入れるのは `meetScan` (既定8) 人まで
- そのうち実際に「出会った」ことにするのは `meetPerTick` (既定2) 人まで
- 同じ相手は `meetCoolSec` (既定45秒) 空けないと数えない

さらに、人混みでは**知っている顔を優先**して見る (`relOf` で並べ替える)。
これをしないと6000人の中で毎回別人とすれ違うだけになり、関係が育たない。

副産物として、`stepNeeds` の孤独判定 (全員を総当たりしていた) も
この空間ハッシュに載せ替えた。

### 18.4 立ち話

出会った2人が確率 `talkP × (0.4 + 親密度)` で `talkSec` 秒立ち止まり、
向き合って頭上に 💬 を出す。

- **狭い道では立ち止まらない** (`openRatio >= TALK_OPEN`)。
  40日目の渋滞問題と同じ失敗をしないための制約。
- 同時に立ち話できるのは `talkMax` (既定6) 組まで。
- 歩行シェーダの振幅は「実際に進んだ距離」で決まるので、足を止めるだけで
  脚のアニメも自動的に止まる (§16.5)。

吹き出しの板は `NEED_ICONS` と無関係に出す。これが無いと
「住民が急に立ち止まった」だけの画になる。

**吹き出しに絵文字を使ってはいけない。** 最初 💬 を焼いたところ、本番 (Linux) では
絵文字フォントが無くて豆腐になった (配信画面の日本語が化けたのと同じ原因)。
いまは SVG の図形だけ (角丸 + しっぽ + 点3つ) で描いていてフォントに依存しない。
`buildTalkBubble`。

### 18.4b 会話ログ (画面左下)

頭上の吹き出しだけでは、配信のカメラ距離で何が起きているか読めない。
チャットログのように左下へ会話を流す。

- 1回の立ち話につき **話し手の一言 + 相手の返し** の2行。
- 文面は `TALK_LINES` のテンプレート。**ASCII の英語のみ** (`_ascii` で最後に落とす)。
- 先にコロンを付けてから名前を切ると、コロンごと落ちて名前と本文がくっつく。
- 新しい行が来たときだけ SVG を焼き直す (最短700ms間隔)。

**折り返し** (`wrapTalkLine`)。街を隠さないよう板は狭く (既定250px・フォント10px)
してあるので、1行に収まらない台詞は折り返す。

- 桁数は**文字数ではなく板の幅から出す** (`TALK_LOG_COLS`)。等幅フォントの
  1文字幅は約 0.6em なので、`TALK_LOG_W` を変えても折り返し位置がズレない。
- 続きの行は2桁ぶん字下げして、誰の台詞の続きか分かるようにする。
- 1語で1行に収まらないとき (長い店名など) は語の途中で割る。
- 表示行数 (`TALK_LOG_ROWS`) は折り返し**後**の行数。板の高さは固定で、
  新しい行がいつも同じ高さに来るよう**下揃え**にする。
- 先頭が「前の会話の折り返しの続き」だけになると、誰の台詞か分からない断片が
  浮いて見えるので、名前のある行が来るまで落とす。

**跡地の再利用に注意。** `foundShop` は跡地を使い回すとき同じキーの `typeIdx` を
書き換えるので、住民の好みのキーが住宅などに化けていることがある。
`CHOOSABLE` で弾かないと「Have you tried the new House?」という会話になる
(実際に一度出た)。`freshShopFor` / `deadShopFor` / `prefBest` を使うところ全部で確かめる。

ティッカーには**話題のあるもの (新店/閉店) だけ**を流す。世間話まで流すと
開店/閉店のニュースを押し出すうえ、左下の会話ログと二重になる。

### 18.5 話題

| 話題 | 効果 |
|---|---|
| `newshop` | 相手が知らない「最近できた店」を教える。少し行きたくなる (`prefBump`) |
| `closed` | もう無い店の話。二人ともその好みを忘れる |
| `place` | 従来の口コミ (行きつけの交換) |

`gossip` は「一番の行きつけ」しか広めないので、**できたばかりの店は誰の一番でもなく
広まらない**。`newshop` がそこを埋める。

`deadShopFor` の条件は**開いている店を拾わないこと**。反転させると健全な店の好みを
会話のたびに消してしまう (実装中に一度間違えた。好みがまだ溜まっていない
時期だったので発火せず、危うく気づかないところだった)。

### 18.6 ニュースの流量制御

人口1000人だと20日で280組の友人ができる。全部ティッカーに流すと
開店/閉店/道のニュースを押し出してしまう。

## 19. 街を広げる — 何が律速か

「前回リソースを削ったので1.5倍に広げられそう」を数字で確かめた。

街の最大の一辺は `GRID` (セル数)。実寸は `GRID x CELL` (CELL=2.0)。
以前はソースに直接書いてあったので、環境変数で変えられるようにした。

### 19.1 実測 (住民1000人・QUALITY=M)

| | GRID=30 (従来) | 45 (1.5倍) | 60 (2倍) |
|---|---|---|---|
| 実寸 | 60x60 | 90x90 | 120x120 |
| 面積 | 1.00x | 2.25x | 4.00x |
| メッシュ | 366 | 880 | 1,514 |
| 描画 | 2.6ms | 3.2ms | 3.9ms |
| 遮蔽フェード | 1.3ms | 1.9ms | 2.4ms |
| 建物 | 139 | 337 | 533 |
| 保存ファイル | 175KB | 223KB | 274KB |
| **1フレーム合計** | **15.2ms** | **15.6ms** | **17.4ms** |

30fps の予算は 33ms なので、**2倍でも収まる**。§16 でメッシュを
5,561 → 352 に削ったぶんがそのまま余白になっている。

### 19.2 律速は描画ではなく経路探索だった

`planPath` は「未確定セルの中から最小を線形走査する」Dijkstra だった。
走査回数は `GRID^4` で効くので、面積2.25倍の45にすると**1回あたり4倍**になる。

これを **A* + 二分ヒープ**に置き換えた。

- 最小の取り出しを二分ヒープに → O(V^2) が O(E log V) に
- 残り距離の見積り (マンハッタン距離) を足して探索セル数そのものを減らす
- 見積りは「マンハッタン距離 x 最小の1手コスト」。`COST_ROAD=1` が最小なので
  マンハッタン距離をそのまま使えば必ず実コスト以下 = **最短経路を見失わない**

| 1回あたり | GRID=30 | 45 | 60 |
|---|---|---|---|
| 旧 (線形走査 Dijkstra) | 0.73ms | 3.41ms | 10.67ms |
| 新 (A* + 二分ヒープ) | **0.025ms** | **0.059ms** | **0.102ms** |
| 速さ | 30倍 | 58倍 | 105倍 |

**照合**: 旧実装を `_planPathSlow` として残し、`/nav?verify=N` で
ランダムな始点終点の最短コストを比べられるようにした。
30/45/60 のいずれでも **一致率 100%** (500/500, 500/500, 300/300)。
経路そのものは同コストなら別ルートでも構わないので、コストだけを比べている。

```
curl "http://localhost:8080/nav?verify=500"
```

### 19.3 GRID を変えると保存済みの街が消える

`loadCity` は `j.grid !== GRID` で保存を捨てる。**広げた瞬間に Day 1 から
やり直しになる** (道も店も人間関係も全部)。24時間配信でこれは大きいので、
広げる前に必ず退避すること。

```bash
cp data/city_state.json data/city_state.backup.json
```

フィールドは `fieldLo = floor((GRID - size) / 2)` で**中央に置かれる**ので、
古い地図を大きい GRID の中央に埋め込んで座標をずらせば、街を保ったまま
広げる移行処理は書ける (未実装)。継ぎ目の道路の接続と
`ensureAllBuildingsReachable` のやり直しが要る。

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `GRID` | 30 | 街の最大の一辺 (セル数・10〜120)。実寸は `GRID x CELL` |

## 20. 地平線とフォグ

フィールドの外を何も描かないでいたので (`rebuildGround` の下地はフィールドぶんだけ)、
街が小さいうちは**板が宙に浮いて見え**、空との境目が曖昧だった。

### 20.1 やったこと

**(a) どこまでも続く地面** — フィールドの外側に大きな板を1枚敷く。
フォグで完全に溶ける距離より外まで伸ばしておけば、板の縁は決して見えない。
板1枚 = 2三角形 = 1ドローコールなので、どれだけ大きくしても負荷は変わらない。
街の下地 (z=0) と重ならないよう `z=-0.05` に沈め、`renderOrder=-1` で先に描く。

**(b) フォグ** — `THREE.Fog` (線形)。**頂点もドローコールも増えない**
(フラグメントシェーダ内の混色だけ)。効き始めと溶けきる距離は街の実寸
`GRID x CELL` を基準にする。

**(c) フォグの色を空に追従させる** — `updateDayNight` が毎フレーム
`S.fog.color` を `S.background` に合わせる。ズレると地平線に色の段差が出る。
昼夜と天気で空の色が変わるので、固定色にはできない。

### 20.2 負荷 (住民1000人・QUALITY=M・GRID=30)

| | 描画 | メッシュ |
|---|---|---|
| 従来 (フォグ無し) | 1.4ms | 395 |
| 地平線 + フォグ | **1.5ms** | 396 |

**+0.1ms・+1メッシュ**。実質ゼロ。

### 20.3 観測 (DINOv2) には影響しない

心配だったのは「学習時の画像にフォグは無いので、方策の入力が変わるのでは」という点。
確認したところ観測は **three.js ではなく自前のレイキャスタ**で作っており、
`renderer.render(scene, ...)` は配信フレームの1か所しかない。
フォグがかかるのは配信画面だけで、train/deploy のズレは起きない。

### 20.4 設定

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `FOG` | 1 | `0` でフォグを切る |
| `FAR_GROUND` | 1 | `0` で遠景の地面を敷かない (従来の「浮島」に戻る) |
| `FAR_COLOR` | `0x93ab74` | 遠景の土地の色 |
| `FOG_NEAR_K` | 0.85 | フォグの効き始め = `GRID x CELL x これ` |
| `FOG_FAR_K` | 3.2 | 完全に溶ける距離 = `GRID x CELL x これ` |

GRID=30 なら実寸60なので、効き始め51・溶けきり192・地面の一辺1200
(カメラの far は1200)。街を広げる (§19) と自動で追従する。

霞みが強すぎる/弱すぎるときは `FOG_NEAR_K` を動かすのが分かりやすい。
小さくするほど手前から霞む。

## 21. お金・仕事・犯罪 (economy.js)

「悪い人が出てくるとドラマが生まれそう」から出発した機能。
ただし**犯罪だけを足すと飾りになる**。犯罪が物語になるのは、それが何かの結果であり、
同時に次の原因にもなるときだけ。そこで最小の因果の環を作った。

```
    店に通う → 金を払う → 店の売上 → 給料 → 生活できる
      ↑                                          ↓
    店が潰れる ← 売上が減る ← 万引き ← 追い詰められる ← 失業・無一文
```

万引きされた店は売上が落ちて人を切る。切られた人がまた追い詰められる。
**犯罪が失業を生み、失業が犯罪を生む**環になっているので、1件の閉店が街に波及する。

### 21.1 用意したステータス

| 住民 | 範囲 | 意味 |
|---|---|---|
| `cash` | 0〜 | 手持ちの金 |
| `desper` | 0〜1 | 追い詰められ度。ゆっくり動く |
| `wanted` | 0〜1 | 疑われ度。日々薄れる |
| `jobless` | -1 or 日数 | 職を失ってから何日目か (-1 = 待ちなし) |
| `crimes` / `jail` | | 前科 / 収監の残り日数 |

| ペルソナ | 意味 |
|---|---|
| `honesty` 0〜1 | 追い詰められても踏みとどまる強さ。既定0.6 |

| 街 | 意味 |
|---|---|
| `CITY.unrest` | 追い詰められている住民の割合 |
| `CITY.stats.crimes` / `jobsLost` | 累計 |

**`honesty` が要**。同じ苦境でも人によって選ぶ道が違うから物語になる。
実測でも Grandma Rose (0.9) は追い詰められ度1.0でも犯行ゼロ、
Night-shift Mika (0.35) / Freelancer Noah (0.5) が先に手を出した。

### 21.2 行動

- **万引き** — 払えず、かつ `desper > honesty` のとき。店の売上が減り `thefts` が増える。
- **スリ** — 立ち話の最中に相手から抜き取る。social.js の出会いに相乗りする。
  被害者との `rel` が大きく下がるので、犯人は街で孤立していく
  (関係が壊れると立ち話も起きにくくなる = 二重の罰)。
- **逮捕** — `wanted` が高いほど見咎められやすい。所持金を失い数日動けなくなる。

### 21.3 実装中に踏んだ3つの落とし穴

**(a) 固定支出が無いと経済が成立しない。**
最初は「店で払う」だけにしていたら、収入だけが積み上がって誰も困らず、
**犯罪が20日で1件も起きなかった** (平均所持金が40→66に増えていた)。
家賃と日々の食費 (`livingCost`) を毎日引くようにして初めて、
「職を失う」が生活に効くようになった。**出ていくものがあって初めて失業が意味を持つ。**

**(b) 店が誰の職場でもなかった。**
`WORK_IDX` はオフィス/銀行/市役所だけで、開店・閉店を繰り返す店 (eat/shop/fun/care) は
誰の職場でもなかった。だから「店が潰れて職を失う」が**構造的に起きない**。
店も雇用の場 (`SHOP_JOB_IDX`・1軒 `SHOP_JOBS` 人) に加えた。

さらに、職場の割当が「リストの先頭から詰める」だったので、オフィスばかり埋まって
店に人が回らなかった。**一番空いている所へ入れる** (`take(..., spread)`) に変更。

**(c) `assignHomes()` が転入時にしか呼ばれていなかった。**
一度失業した人が永久に職を探せず、**1000人全員が無職・unrest 1.0・万引き397件**という
街の崩壊が起きた。日次で職探しを回すようにした。
併せて `jobless` の意味を整理した — 「無職かどうか」は `work`/`owns` の有無で決まり、
`jobless` はあくまで再就職までの待ち時間カウンタ。ここを混同していたため、
起動直後に全員が求職待ちになっていた。

**(d) `loadPersonaDefs` がホワイトリスト**だったので、`personas.json` に足した
`honesty` も `sociability` も黙って既定値に落ちていた。§18 の社交性も
実は効いていなかった。追加する項目はここにも書くこと。

### 21.4 実測

**健全な小さい村** (34人・20日): 失業3→再就職3、**犯罪0**。
仕事があるうちは誰も追い詰められない。これが正しい挙動。

**大きい街** (1000人・12日): 失業率7.7%、`jobsLost` 378 / `jobsFound` 299、
unrest 0.021、前科者10人、万引き9件。**犯罪は稀で、起きると意味がある**水準。

ニュース例:
```
💼 💊 薬局 が閉じて 9人が職を失った
🚨 Night-shift Mika #2 が Retired Artist Haru #1 から金を抜き取り捕まった
🕶 Teen Jay #2 が 🍜 ラーメン屋 で万引きした
```

通行性 0.563 / 1フレームの負荷は導入前と変わらず (日次処理なので毎フレームには乗らない)。

### 21.5 見かた

```
curl http://localhost:8080/economy
```

`jobs` (店勤め/オフィス勤め/店主/無職) は、犯罪が起きないときの切り分けに使う。
`atShop` が 0 なら (b) の状態に戻っている。

### 21.6 設定

|---|---|---|

| `CRIME` | 1 | `0` で犯罪だけ無効 (経済は動く) |

### 21.7 まだ無い抜け道 (次に足すなら)

## 22. 警察署と警官

§21 では「見咎められたら即逮捕」という確率ロールで済ませていた。
街に取り締まる主体が居ないので、犯罪が起きても誰も動かない。
警察署を建物として置き、そこに勤める住民が手配犯を追いかけるようにした。

### 22.1 建物タイプを足すときの決まりごと

`BLDG_TYPES` への追加は**必ず末尾**にすること。途中に挿すと `typeIdx` がずれて
保存済みの街 (`data/city_state.json`) の建物が全部別物に化ける。

末尾なら安全である理由:

- 既存の `typeIdx` 0〜24 はそのまま
- 学習済みモデルの goal クラス (`meta.bldgToZ`) に無い型は
  `goalZ=null` になるだけで、方策側は素通しする (到着判定は別経路)
- `seenMask` のビット演算は `1<<25` まで問題ない (32bit に収まる)
- `loadCity` は建物数を見ていないので保存の互換も保たれる

テクスチャは仮のもの (`textures/v4/police.jpg`) を SVG から起こして置いてある。
他の建物と同じ縦長。差し替えるときは同じパスに上書きするだけでよい。

**初期生成には混ぜない** (`NO_SPAWN`)。警察署は「治安が悪くなったから建てた」もので、
最初から街に散らばっているものではない。混ぜたところ 9軒建って警官が114人になった。

### 22.2 警官

`WORK_IDX` に `police` を足したので、警察署は職場として扱われ、
そこに割り当てられた住民が警官になる (`isCop`)。特別な種族ではなく、
**普通の住民が警察署に勤めているだけ**。警察署が潰れれば警官も失業する。

### 22.3 目撃と逮捕を分けた

以前は「見咎められた = 逮捕」だったが、これを2段階にした。

- **目撃** — 犯行時に見られると `wanted` が上がる。ニュースは 👀。
- **逮捕** — 手配中の住民を**警官が見つけて追いかけ、詰めたら確保**。ニュースは 🚓。

この分離により、**警察署が無い街では誰も捕まらない**。前科だけが積み上がり、
治安が悪いままになる。だから街は警察署を建てる動機を持つ。

追跡は既存のナビ (`enterNavigateTo`) をそのまま使い、相手が動くので数秒ごとに
経路を引き直す。A* が 0.01ms/回 なので引き直しは負荷にならない (§19)。
俯瞰カメラで2つの点が近づいていくのが見えるので配信としても分かりやすく、
会話ログにも `Stop right there, ...` / `All right, all right...` が出る。

### 22.4 街が警察署を建てる

`unrest` が閾値を超えるか、累計犯罪が `POLICE_CRIME_MIN` を超えたら建てる
(`maybeFoundPolice`)。建てる場所は手配中の住民が多いあたりを優先する。

**1軒目も「必要になってから」建てる。** 平和な村に最初から警察署があると
「治安が悪くなったので建てられた」という筋が消える。実測でも、犯罪ゼロの
34人の村では `stations: 0` のままだった。

### 22.5 実測 — 3日にわたる筋

```
Day 9  👀 Homebody Lily #7 が 🥩 牛丼屋 で万引きするのを見られた
Day 10 👀 Night-shift Mika #33 が 🍜 ラーメン屋 で万引きするのを見られた

Day 12 🚓 Night-shift Mika #14 が Night-shift Mika #33 を逮捕した
```

1000人・15日で 警察署2軒 / 警官28人 / 追跡66回 / 逮捕16件、unrest 0.045。
1フレームの負荷は導入前と変わらず (経路探索は 1回0.01ms・10秒あたり計11ms)。

### 22.6 直した2つ

- **追跡対象が消えても `chase` が外れなかった** — 手配犯2人に対して
  「追跡中の警官」が12人になっていた。相手が見つからないときも外すようにした。
- **`CAT_LABEL` に `civic` が無く**「undefined が足りなくなり」というニュースが出ていた。

## 23. 学校と通学 / すべての建物に採算を

### 23.1 ランドマークタワーが3本並んでいた原因

本番で人口500人の街にランドマークタワーが3本建っていた。原因は2つ。

**(a) 初期生成が発展段階を無視していた。** `planStructures` は `FP1_IDX`/`FP2_IDX` から
無差別に引いていて、`typeAllowed`（発展段階ごとの高さ上限）を見ていなかった。
集落の段階でも高さ3.3のタワーが生成されうる。
→ `pickGenType` で生成時も上限を尊重するようにした。**新規の街にタワーは生成されない**。

**(b) 職場は構造的に絶対潰れなかった。** `isClosable` は `CLOSABLE_CATS`
（飲食/買い物/遊び/医療）しか見ておらず、`work`/`home`/`civic`/`tour`/`transit` は
どれだけ余っていても閉じる道が無かった。`markVacant` は「誰も使っていない」ものだけが対象で、
タワーには従業員が割り当てられるので永久に対象外だった。

### 23.2 建物の採算 — ただし対象は絞る

`economy.js` に建物の収支を入れた。

```
維持費 = upkeepUnit x footprint^2 x height
収入   = 職場: min(従業員, 定員) x workerOutput
         住宅: min(住人, 定員) x rentPerHead
         公共: 人口 x civicPerHead / 公共施設の軒数   (街の予算を分け合う)
         来客: 支払いの積み上がり (revenue)
定員   = capUnit x footprint^2 x height
```

**収入は定員で頭打ちにする。** 定員超過で詰め込まれた人数まで income に数えると、
人口の多い街ではどんな大きさの建物も黒字になり、大きすぎる建物が潰れない
（実測: 1000人の街にタワーが10本残った）。

**街の発展段階に対して大きすぎる建物は維持費が `oversizePenalty` 倍。**
集落にランドマークが建っていて採算が合わないのは当たり前で、
これが無いと「昔の生成で建った巨大な建物」が永久に残る。

### 23.3 対象を絞った理由 — 一度街を殺した

最初は「赤字が続いた建物はすべて畳む」という一本の規則にした。結果:

```
職場が減る → 失業 → 誰も払えない → 店が潰れる → さらに職場が減る
```

**実測: 失業34% / 無一文316人 / 1000人の街に店2軒**。街が空洞化した。

そこで `bankruptSweep` が畳むのは **「街の発展段階に対して大きすぎる建物」だけ** にした。

- 来客で稼ぐ店の淘汰は既存の `maybeClose`（同業と比べて悪い店を閉じる）が担う。
  あれは同業が減れば止まる**自己制限**がある。絶対額の赤字で畳むとその歯止めが無い。
- 職場・住宅の「余り」は `markVacant`（使われていないもの）が担う。
- 大きすぎる建物だけなら、身の丈に戻った時点で自然に止まる。

**実測（既存のタワー10本の街）**: タワー10→0、市役所1軒閉鎖。
店・住宅・オフィスは無事、unrest 0.053。
**実測（新規の村・20日）**: 採算閉鎖 0件。そもそも大きすぎる建物が生成されない。

### 23.4 学校

学齢別に4つ追加した（既存の `school`(17) は総合的な学び舎として残す）。

| | footprint | height | 建てられる段階 |
|---|---|---|---|
| 小学校 `elementary` | 1 | 1.1 | 集落から |
| 中学校 `junior` | 1 | 1.4 | 集落から |
| 高校 `high` | 2 | 1.7 | 町から |
| 大学 `university` | 2 | 2.1 | 町から |

**小学校と中学校は 1x1。** `footprint:2` は「町」以上でしか建てられないので、
2マスにすると村に子どもが居ても学校が建たない（実際に建たなかった）。

通学するペルソナは `SCHOOL_OF_PERSONA`（`personas.json` の `schoolLevel` でも指定可）。
Toddler Sora / Curious Kid Mia → 小学校、Student Yui → 中学校、
Teen Jay / Athletic Teen Riku → 高校、Freelancer Noah → 大学。

- **平日だけ**通う（`isWeekend`: 7日のうち後ろ `WEEKEND_DAYS` 日が休み）。
- 通学時間は `SCHOOL_FROM`〜`SCHOOL_TO`（既定 8〜15時）。
- 学齢に合う学校が無ければ他の段階で代用する（小学校しか無い村では中学生もそこへ）。
- 学生が居るのに学校が無ければ街が建てる（`maybeFoundSchool`）。初期生成には混ぜない。

**学生は「無職」ではない。** 通学が本業で、家から仕送り（`allowance`）が出る。
ここを外したところ、子どもが全員「無職・無一文」になって犯罪に走った
（実測: 28人の村で犯罪44件。仕送りを入れて0件に戻った）。

**実測の通学**: 平日は 8時に0人 → 昼過ぎに 5〜7人/11人が校内、15時を過ぎると減っていく。
`WEEKEND_DAYS=7`（全日休み）にすると終日 `inSession:false` で登校も止まる。

```
curl http://localhost:8080/school
```

### 23.5 建物タイプを足すときの決まりごと (再掲)

**必ず末尾に足す。** 途中に挿すと `typeIdx` がずれて保存済みの街が壊れる。
いま30種（0〜29）。`seenMask` のビット演算は `1<<29` で32bitに収まる。
初期生成に出したくないものは `NO_SPAWN` に入れる（警察署・学校4種）。

### 23.6 設定

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `BANKRUPT` | 1 | `0` で採算による閉鎖を無効 |
| `UPKEEP_UNIT` | 8.75 | 維持費の係数 |
| `CAP_UNIT` | 2.5 | 定員の係数 |
| `WORKER_OUTPUT` | 7 | 従業員1人が1日に生む価値 |
| `RENT_PER_HEAD` | 5 | 住人1人あたりの家賃 |
| `CIVIC_PER_HEAD` | 0.22 | 人口1人あたりの税収 |
| `OVERSIZE_PENALTY` | 3.0 | 大きすぎる建物の維持費倍率 |
| `BANKRUPT_DAYS` | 5 | 赤字が続いて閉鎖するまで |
| `WEEKEND_DAYS` | 2 | 7日のうち後ろ何日が休みか |
| `SCHOOL_FROM` / `SCHOOL_TO` | 8 / 15 | 通学時間 |
| `SCHOOL_PER_STUDENT` | 40 | 学校1つが受け持つ人数 |
| `ALLOWANCE` | 10 | 学生の仕送り |

## 24. 見た目の底上げ (負荷ほぼゼロ)

「ライティングやマテリアルの工夫で見た目を良くしたい。ただし負荷は上げたくない」。
**ドローコールを増やさない**ことを条件に、効く順に入れた。

### 24.1 いちばん効いたのは光の比

以前は 環境1.3 + 半球1.1 に対して 平行光1.55。回り込みが強すぎて
**どの面もほぼ同じ明るさになり、箱に立体感が無かった**。

```
旧: sun 0.15+1.55d / amb 0.45+0.85d / hemi 0.25+0.85d
新: sun 0.18+2.35d / amb 0.30+0.38d / hemi 0.20+0.50d
```

環境を落として平行光を上げるだけで、陽の当たる面と陰の面に差がつき形が見える。
**負荷はゼロ**。`LIGHT_KEY` / `LIGHT_FILL` で好みに寄せられる。

### 24.2 接地感 (アンビエントオクルージョン) — ドローコール0

建物や木の際の地面を暗くする。これが無いと建物が地面に乗っているのではなく
板の上に浮いて見える。

地面はもともと `road`/`grass`/`wear1`/`wear2` の4メッシュにまとめてあるので、
**頂点カラー属性を足すだけ**で済む。メッシュもドローコールも増えない。
セルの四隅ごとに、隣接する建物/木の数から明るさを決める (`cornerAO`)。
辺2つが塞がっている隅がいちばん暗い — Minecraft 式の滑らかな AO と同じ考え方。

同時に、セルごとの微妙な明暗のばらつき (`AO_NOISE`) も同じ頂点カラーに乗せた。
一面べったり同じ色だと「板」に見える。位置から決まる固定値なのでちらつかない。

### 24.3 空のグラデーション — 1メッシュ

`scene.background` の単色だと上も下も同じ色で「箱の中」に見える。
内側を向いた球 (16x10) に頂点カラーでグラデーションを焼き、
天頂を濃く・地平をフォグと同じ色にした。

**地平の色をフォグと一致させるのが要**。ずれると遠景の地面との境目に段差が出る。
昼夜と天気で空の色が変わるので、`updateDayNight` が毎フレーム塗り直す
(球の頂点は数百個なので誤差の範囲)。

**カメラを固定して計測したところ、ドームの有無で描画時間に差は出なかった**
(4.9 / 4.3 / 5.4 / 4.9ms)。画角が変われば1ms前後ぶれるので、
最初「+1.6ms」と読めたのは画角によるノイズだった。

### 24.4 同じものが並んで見えないように — 追加コストゼロ

**建物**: 同じテクスチャが並ぶと「コピー」に見える。座標から決まる固定の色味を掛ける。
マテリアルはもともと1軒ずつ clone しているので**追加コストはゼロ**。

**木**: 一度 1本ずつ大きさ (0.82〜1.24倍)・緑の濃さ・向きを振ってみたが、
**戻した**。幹も葉も「箱」なので、回すと立方体が菱形に見えて、
揃っているときより不自然だった。大きさのばらつきも、角ばった見た目とは噛み合わない。
この街のブロック的な絵柄では、木は揃っているほうが素直に見える。

### 24.5 雨の日は地面が濡れる — 負荷ゼロ

雨のとき地面の色を 0.8 倍にする。`rebuildGround` が20秒ごとに走るので、
天気が変わると自然に切り替わる。色を変えるだけなので負荷は無い。

### 24.6 設定

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `LIGHT_KEY` | 1.0 | 平行光 (陽射し) の強さ。上げるとコントラストが強くなる |
| `LIGHT_FILL` | 1.0 | 環境光 (回り込み) の強さ。上げると眠くなる |
| `GROUND_AO` | 1 | `0` で接地の陰影を切る |
| `AO_DEPTH` | 0.42 | 建物際をどこまで暗くするか |
| `AO_NOISE` | 0.05 | セルごとの明暗のばらつき |
| `SKY_DOME` | 1 | `0` で単色の空に戻す |
| `BLDG_TINT` | 0.10 | 建物ごとの色のばらつき |

### 24.7 やらなかったこと

- **影 (shadow map)** — 深度パスがもう1回増える。本番の Linux はソフトウェア描画
  なので、全画面ぶんの塗りが2回になるのは割に合わない。
  接地の AO で「浮いて見える」問題は解消しているので、費用対効果が低いと判断した。
- **MeshPhong / MeshStandard** — フラグメントごとの計算になる。
  建物は箱で頂点が少なく、Lambert (頂点ごと) で足りている。
  ソフトウェア描画ではフラグメント側を増やすのがいちばん高くつく。
- **ポストプロセス (bloom / SSAO)** — 全画面パスが増えるので同じ理由で見送り。

## 25. 街を作り直す手段を3つに増やした

これまで街のリセットは `/city?reset=1` だけで、**HTTP を外から叩ける経路が要る**のが
前提だった。本番はポートを外に開けていないので、SSH で入って curl するしかない。

そこで実装を `doCityReset(newMap)` 1つにまとめ、呼び口を3つにした。

| 経路 | 使いどころ |
|---|---|
| `GET /city?reset=1` | ローカル / 開発中 (`&newmap=1` で地形も引き直す) |
| **`SIGUSR2`** | 本番。ポートが開いていなくても叩ける |
| WebSocket `newmap` | `client.html` のUI |

`SIGUSR1` は Node がデバッガ用に予約しているので使わないこと。

### 25.1 pid ファイル

起動時に `data/server.pid` へ自分の pid を書き、終了時に消す。
pm2 でも systemd でも、これがあれば `tools/city-reset.js` がプロセスを見つけられる。
`.gitignore` 済み。

### 25.2 CLI

```
node tools/city-reset.js            稼働中のサーバに SIGUSR2 を送る
node tools/city-reset.js --status   いまの街を見るだけ (何も変えない)
node tools/city-reset.js --file     サーバ停止中に保存ファイルを外す
node tools/city-reset.js --pid=1234 pid を直接指定
```

**どの経路でも実行前に `data/city_state.<日時>.bak` へ退避する。** 戻したいときは
名前を戻すだけ。街の蓄積は取り返しがつかないので、消す前に必ずコピーを取る。

`--file` は「サーバを止めている」ことが前提。動いたまま実行すると、
次の自動保存 (`CITY_SAVE_SEC`) で今の街が書き戻される。CLI もそう警告する。

### 25.3 実測

Day 6 (人口14 / 開業6 / 閉店3 / 友人7) の街に SIGUSR2 を送り、
Day 1 (人口8 / 累計すべて0) に戻ることを確認。
`--file` 経路も、保存を外して起動すると新しい街から始まることを確認。

リセットは `buildScene` + `initAgents` をやり直すので**数秒かかる**。
送った直後に `--status` を見てもまだ古い値が出る (実装中にこれで混乱した)。
サーバのログに `[City] Day 1 から作り直しました` が出てから確認すること。

## 26. 配信に BGM を載せる

音声はこれまで `anullsrc` (無音) を ffmpeg に入れていた。ここを差し替えるだけで曲が載る。

```
YT_MUSIC=./music              ディレクトリ … 中の音声ファイルを順に流す
YT_MUSIC=./music/theme.mp3    ファイル      … その曲をループ
YT_MUSIC_VOL=0.35             送出時の音量 (曲そのものは触らない)
YT_MUSIC_SHUFFLE=0            名前順にする (既定はシャッフル)
```

対応拡張子は mp3 / m4a / aac / ogg / opus / flac / wav。
見つからなければ警告を出して**無音のまま配信を続ける** (止めない)。

### 26.1 ループのやり方でハマった

素直に `-stream_loop -1` を付ければ良いと思ったが、**concat デマクサには効かない**。
ffmpeg 8.1.2 で実測したところ:

| 指定 | 素材9秒で15秒の出力を作れるか |
|---|---|
| 単一ファイル + `-stream_loop -1` | **15.02秒** ○ |
| concat + `-stream_loop -1` | **9.63秒** ✗ (`Operation not permitted`) |
| concat (一覧を繰り返し書く) | **15.00秒** ○ |

**これは致命的**で、音声が尽きた時点で ffmpeg が出力を閉じる = 配信が止まる。
実際、最初の実装では出力が9.1秒 (プレイリスト長ちょうど) で終わっていた。

そこで:
- **単一ファイル** … `-stream_loop -1` (正しく効く)
- **ディレクトリ** … concat の一覧に**同じ並びを `YT_MUSIC_REPEAT` 回書く** (既定200)。
  1曲4分・3曲なら約400時間ぶん。ここが尽きると配信が止まるので多めに取る。

### 26.2 実際に鳴っているかを確かめた

「音声ストリームが存在する」だけでは無音を配信しかねないので、
PCM に落として振幅を測った:

| | 最大 | RMS |
|---|---|---|
| 配信ファイル (BGM入り) | 2870 | 1943 |
| 元の mp3 | 3896 | 2751 |
| `anullsrc` (無音) | 0 | 0 |

`-af volume=0.35` を掛けたぶんだけ元より小さく、無音ではないことを確認。

### 26.3 その他

- `-re` を付けて実時間で読む。映像は Node がパイプへ実時間で書くので勝手に律速されるが、
  音声には歯止めが無く、付けないと ffmpeg が先読みで暴走する。
- `-shortest` は**付けない**。音声が何かの拍子に尽きたとき、配信ごと止まってしまう。
- ffmpeg が再起動すると曲は最初から。24時間配信なら気にならないが、
  毎回同じ曲順が嫌なら `YT_MUSIC_SHUFFLE=1` (既定) で起動ごとに並びが変わる。
- 一覧は `data/music_playlist.txt` に書き出される (`.gitignore` 済み)。

### 26.4 著作権について

24時間の公開配信で市販の音楽を流すと、YouTube の Content ID で
**ミュート・ブロック・収益化停止**の対象になる。曲は
ロイヤリティフリーのもの (YouTube オーディオライブラリ / 自作 / 明示的に配信許諾のあるもの)
を使うこと。判定は自動なので「短いから」「BGMだから」は通用しない。
